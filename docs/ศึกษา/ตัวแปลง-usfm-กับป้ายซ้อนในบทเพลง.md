# ตัวแปลง USFM อ่านป้ายซ้อนใน `\qs` ไม่ออก — เราไปหาเอกสารของเจ้าของมาแล้ว

ใบงาน [#83](https://aimgit.aimagin.com/v3/phrakham/-/issues/83) · คำขอรวม [!76](https://aimgit.aimagin.com/v3/phrakham/-/merge_requests/76)

## ทำไมต้องมีไฟล์นี้

รอบก่อนเราเปิดโค้ดของเจ้าของตัวแปลงอ่านเอง แล้วสรุปว่า "เป็นรู" โดยยังไม่ได้ไปหาเอกสารของเขา

พี่เอมทักว่า คนที่ทำเครื่องมือให้คนทั้งโลกใช้ ต้องเขียนบอกว่ารองรับอะไรไม่รองรับอะไร ถ้าเราหาไม่เจอ แปลว่าเราหาไม่พอ และเราเพิ่งพลาดแบบเดียวกันในใบ 84 มาแล้ว คือตั้งกฎเองอยู่นาน พอเปิดคู่มือ เจ้าของบอกวิธีไว้แล้วตั้งแต่แรก

ไฟล์นี้คือผลของการไปหาเอกสารรอบนั้น

## เรื่องที่กำลังพูดถึง

ฉบับ WEB เขียนคำว่า Selah แบบนี้

    \qs \+w Selah|strong="H5542"\+w*.\qs*

ป้าย `\qs` คือป้ายบทเพลง ข้างในมีป้าย `\+w` ซ้อนอยู่ เครื่องหมายบวกคือวิธีเขียนป้ายซ้อนของ USFM

ตัวแปลงอ่านตรงนี้ไม่ออก มันทักว่าผิด แล้วคาย `<char style="qs"/>` เปล่า ๆ ออกมา คำว่า Selah หายทั้งคำ ฉบับ WEB โดน 17 จุด อยู่ในสดุดี 14 จุด กับฮาบากุก 3 จุด

## ข้อสรุป — เข้าทางที่หนึ่ง เขาบอกว่ารองรับ แต่ของจริงไม่รองรับ

**เขาไม่เคยเขียนไว้ที่ไหนเลยว่าไม่รองรับ** ตรงกันข้าม เขาประกาศว่ารองรับ USFM รุ่น 3 ทั้งหมด และประกาศว่าเดินตามมาตรฐานของคณะกรรมการ USFM/X

**และโค้ดของเขาเองก็ขัดกันเอง** ฝั่งตัวแปลงจัด `qs` เป็นป้ายชนิดตัวอักษรเต็มตัว แต่ฝั่งไวยากรณ์ไม่ได้จัดแบบนั้น สองฝั่งอยู่ในที่เก็บเดียวกัน

⇒ นี่ไม่ใช่ข้อจำกัดที่เขาตั้งใจ เป็นของที่หลุด

**แต่ต้องพูดให้ตรง** ไม่มีประโยคไหนในเอกสารของเขาที่พูดถึงป้ายซ้อนใน `\qs` โดยตรง ทั้งฝั่งรองรับและฝั่งไม่รองรับ สิ่งที่เขาเขียนคือคำประกาศแบบคลุมทั้งก้อน ⛔ ไม่ใช่คำสัญญาเฉพาะเรื่องนี้

## หลักฐานที่แรงที่สุด — โค้ดของเขาขัดกันเอง

นี่คือข้อที่ควรเอาไปบอกเจ้าของ เพราะเขาเปิดไฟล์ตัวเองดูแล้วเห็นทันที

**ฝั่งตัวแปลง จัด `qs` เป็นป้ายชนิดตัวอักษร** ไฟล์ `py-usfm-parser/src/usfm_grammar/usx_generator.py` มีรายชื่อชื่อ `CHAR_STYLE_MARKERS` และ `qs` อยู่ในนั้น อยู่ในกลุ่มที่เขาเขียนกำกับว่า Special-text

บรรทัดถัดมาเขาสร้างรายชื่อป้ายซ้อนขึ้นจากรายชื่อนั้นตรง ๆ โดยเอาคำว่า Nested ไปต่อท้ายทุกชื่อ ⇒ **แปลว่าตัวแปลงของเขาเตรียมช่องชื่อ `qsNested` ไว้รับแล้ว**

ฝั่งเว็บกับฝั่ง node ก็เหมือนกัน `web-usfm-parser/src/filters.js` และ `node-usfm-parser/src/filters.js` มี `qs` อยู่ในรายชื่อ `CHARACTERS` กลุ่ม Special-text

**ฝั่งไวยากรณ์ ไม่ได้จัดแบบนั้น** ไฟล์ `tree-sitter-usfm3/grammar.js`

- รายชื่อ `_characterMarker` มี 31 ชื่อ ⇒ **ไม่มี `qs`**
- รายชื่อ `_nestedCharacterMarker` มี 31 ชื่อ ⇒ **ไม่มี `qsNested`**
- `qs` ไปอยู่ในก้อนบทเพลงแทน เนื้อของมันคือ `_poetryContent`

⇒ **ช่อง `qsNested` ที่ตัวแปลงเตรียมไว้ ไม่มีทางมีของมาลงเลย เพราะไวยากรณ์ไม่เคยปั้นชื่อนั้นออกมา**

⇒ นี่คือของที่หลุด ⛔ ไม่ใช่การตัดสินใจ

## ทางเดินของกฎ — เดินให้ครบทุกขั้น

คนอ่านรอบหน้าต้องเดินตามเองได้ ทางเดินเต็มมีแบบนี้

    qs                  ⇒ เนื้อคือ _poetryContent
    _poetryContent      ⇒ มีสามชื่อ _paragraphContent กับ qac กับ qs
    _paragraphContent   ⇒ มี verseText อยู่ด้วย
    verseText           ⇒ มี text กับ _characterMarker กับ fig

**ตรงนี้ยังไม่ใช่สุดทาง เดินต่อได้อีก**

    _characterMarker    ⇒ มี nd wj w และอื่นรวม 31 ชื่อ
    nd                  ⇒ เนื้อคือ _innerText
    _innerText          ⇒ มี _nestedCharacterMarker อยู่ด้วย

⇒ **ป้ายซ้อนไปถึงได้จากฝั่งบทเพลง แต่ต้องมีป้ายชนิดตัวอักษรห่อไว้อีกชั้นก่อน**

⇒ สิ่งที่ไม่มีกฎรองรับจริง ๆ คือ `\+w` ที่อยู่ใต้ `\qs` **ตรง ๆ** เพราะ `qs` เองไม่ได้ถูกจัดเป็นป้ายชนิดตัวอักษร

## ฝั่งมาตรฐานว่าอย่างไร

มาตรฐานมีสองสำนวน เขียนคนละแบบ แต่บอกเรื่องเดียวกัน ⇒ **เราเปิดทั้งสองแล้ว**

**สำนวนที่เราใช้จริงในด่านของเรา** ⇒ ที่เก็บ `paranext/usfm-tools` ไฟล์ `src/usx-3.1.rng` (2048 บรรทัด) ⇒ นี่คือไฟล์ที่ `tools/ด่านแบบแผนusx.py` โหลดมาใช้อยู่แล้ว

- ก้อน `Char.char.style.enum` มี `qs` อยู่จริง เขียนกำกับไว้ว่า Poetry text, Selah
- ก้อน `CharContent` เปิดให้ข้างในมี `CharEmbed` ได้ ⇒ `CharEmbed` คือป้าย char ที่ซ้อนอยู่ข้างใน และเนื้อของมันก็เป็น `CharContent` อีกที ⇒ ซ้อนซ้ำได้

**สำนวนอีกอัน** ⇒ ที่เก็บ `ubsicap/usx` ⛔ สาขา `main` ไม่มี ต้องใช้ `master` ⇒ ไฟล์ `schema/usx.rnc`

- ก้อน `Char.char.style.enum` มี `qs` เหมือนกัน กำกับว่า Poetry text, Selah
- ก้อน `Char` เปิดให้ข้างในมี `Char` ซ้อนได้ เขาเขียนกำกับไว้เองว่าเป็นป้ายตัวอักษรซ้อน

⇒ **มาตรฐานทั้งสองสำนวนบอกตรงกันว่า `qs` เป็นป้ายชนิดตัวอักษร และป้ายชนิดตัวอักษรใส่ป้ายซ้อนข้างในได้** ⇒ ตรงกับที่ตัวแปลงของเขาจัดไว้ แต่ไม่ตรงกับไวยากรณ์ของเขา

⚠️ **คนตรวจรอบสองทักว่าชื่อ `usx-3.1.rng` กับ `CharContent` ไม่มีอยู่จริง ⇒ ข้อทักนั้นไม่ถูก** เขาไปค้นที่เก็บ `ubsicap/usx` ซึ่งใช้คนละสำนวน จึงไม่เจอ ⇒ ของจริงอยู่ที่ `paranext/usfm-tools` ตามที่อยู่ข้างบน ⇒ **สิ่งที่ขาดจริงคือเราไม่ได้บอกชื่อที่เก็บไว้** ⇒ แก้แล้วโดยเติมชื่อที่เก็บ ⛔ ไม่ใช่เปลี่ยนชื่อไฟล์

ดึงที่เก็บลงมาก่อน แล้วยืนอยู่ในโฟลเดอร์นั้น

    git clone --depth 1 https://github.com/Bridgeconn/usfm-grammar.git ug && cd ug

นับไฟล์คู่มือ ⇒ ได้ **15**

    git ls-files '*.md' | wc -l

นับไฟล์ข้อมูลทดสอบ ⇒ ได้ **298** ⇒ แยกเป็น `tests/` 287 กับ `tree-sitter-usfm3/test/` 11

    git ls-files 'tests/**' 'tree-sitter-usfm3/test/**' | grep -E '\.(usfm|txt)$' | wc -l

ดูของ 5 ไฟล์ที่ทำให้รอบก่อนนับได้ 303 ⇒ คือของนอกสองโฟลเดอร์นั้น

    git ls-files | grep -E '\.(usfm|txt)$' | grep -vE '^(tests/|tree-sitter-usfm3/test/)'

⛔ **ใช้ `git ls-files` ⛔ ไม่ใช่ `find`** เพราะ `find` จะกวาด `node_modules` กับของที่สร้างระหว่างทางเข้ามาด้วย ⇒ นับได้ไม่ซ้ำเดิม

## แล้วจะทำอะไรต่อ

⏸ **ยังไม่ส่งรายงานให้เจ้าของ** การเปิดเรื่องในที่เก็บของคนอื่นเป็นการเผยแพร่ ⇒ รอพี่เอมเคาะก่อน ที่รับเรื่องคือ <https://github.com/Bridgeconn/usfm-grammar/issues>

ระหว่างนี้เราเติมมือเองที่ `tools/แปลงusfmเป็นusx.mjs` ⇒ วันไหนเขาอุดรู เทสชื่อ `ตัวแปลงยังอ่านป้ายซ้อนใน \qs ไม่ออก` จะเปลี่ยนเป็นแดง นั่นคือสัญญาณให้ลบกฎเติมมือทิ้ง

## อะไรที่ยังไม่พิสูจน์

**ยังไม่ได้เปิดหน้าเว็บตัวอย่างของเขาที่ `usfmgrammar.vachanengine.org`** ⇒ เปิดแต่เอกสารในที่เก็บกับที่ติดมากับรุ่นที่เราใช้

**ยังไม่ได้ไล่ที่เก็บของคณะกรรมการ `usfm-bible/tcdocs` ทั้งก้อน** ⇒ ดูแต่ชุดทดสอบที่เขาคัดมาไว้ในที่เก็บของเขาแล้ว ⇒ ยังไม่รู้ว่าคณะกรรมการเองมีเทสเคสนี้ไหม ถ้าไม่มี แปลว่าช่องโหว่นี้มาจากต้นทาง ⛔ ไม่ใช่เขาทำหล่น
