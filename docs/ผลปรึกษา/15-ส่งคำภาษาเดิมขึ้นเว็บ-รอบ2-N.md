### ข้อ 1: การจัดสัดส่วนและรับมือข้อมูลภาษาเดิม 113 Megabytes บนเว็บแบบ Static

เพื่อเปรียบเทียบข้อดีข้อเสียของทั้ง 3 แนวทางหลัก ควบคู่กับทางเลือกที่ 4 สำหรับผู้สูงอายุไทยที่เปิดเว็บบนมือถือด้วยอินเทอร์เน็ตที่ช้า:

| มิติการเปรียบเทียบ | ก. ฝังลงใน HTML ของบทนั้นโดยตรง | ข. แยกเป็น JSON รายบท (1,190 ไฟล์) | ค. แยกเป็น JSON รายเล่ม (66 ไฟล์) |
| :--- | :--- | :--- | :--- |
| **ผลต่อ Google Index (SEO)** | **ดีที่สุดทางทฤษฎี** บอตสามารถไต่เก็บตัวอักษรภาษาเดิมได้ทั้งหมดโดยตรง | **ปานกลาง** บอตจะเก็บตัวบทแปลภาษาไทยหลักได้สมบูรณ์ แต่จะไม่ไต่ไปอ่านตัวภาษาเดิม | **ปานกลาง** เช่นเดียวกับข้อ ข. |
| **ผลต่อเวลาสร้างเว็บ (Build Time)** | **แย่ที่สุด** ทรัพยากรเครื่องสร้างเว็บต้องประมวลผล HTML ที่บวมจัด 1,190 หน้า | **ดีที่สุด** เจเนอเรตหน้า HTML ไทยเบา ๆ ได้รวดเร็ว และพ่นไฟล์ JSON ลงในโฟลเดอร์ Public | **ดี** สร้างเว็บเร็ว แต่ช้ากว่าข้อ ข. เล็กน้อยตอนจัดกลุ่มข้อมูลระดับเล่ม |
| **ผลต่อคนเน็ตช้า (ผู้สูงอายุสัมผัสหน้าจอ)** | **แย่ที่สุด** หน้าเว็บมีขนาดบวมพุ่งสูงถึงหน้าละ 150KB–300KB โหลดช้ามากจนน่าหงุดหงิด | **ดีที่สุด** หน้าแรกโหลดเร็วมากเพราะขนาดน้อยกว่า 15KB และจะโหลด JSON เฉพาะตอนกดสลับดูภาษาเดิม | **แย่** หากเปิดเล่มใหญ่อย่างสดุดี (150 บท) ผู้ใช้ต้องโหลด JSON เล่มขนาดใหญ่หลายเมกะไบต์ในทีเดียว |

*   **สิ่งที่ตำราพูดจริง (Peter Morville - Information Architecture):**
    *   **ความหลากหลายของข้อมูลและสเกลข้อมูล (Heterogeneity & Scale):** ใน Section 5.1.2 ระบุว่า ข้อมูลในเว็บมีความหลากหลายของฟอร์แมตและต้องการการจัดการในระดับความละเอียด (Granularity) ที่แตกต่างกัน [1, 2]. การซอยคอนเทนต์ออกเป็นชิ้นเล็ก ๆ (Chunks) แล้วเชื่อมโยงกันอย่างเป็นระบบ (Section 12.6) จะช่วยให้ระบบสารสนเทศขนาดใหญ่ทำงานได้อย่างมีประสิทธิภาพและยืดหยุ่น [1, 3, 4].
    *   **พฤติกรรมการค้นหาของผู้ใช้:** Morville ระบุว่า ผู้ใช้งานมักสลับโหมดการทำงานระหว่างการค้นหาและการเลือกดู (Searching and Browsing) เสมอ [1, 5]. 
*   **สิ่งที่ผมวิเคราะห์/อนุมานเอง:**
    *   **แนวทาง ข. ดีที่สุดในทางปฏิบัติ** เนื่องจากผู้ใช้กลุ่มนี้ส่วนใหญ่ต้องการ "อ่านพระคัมภีร์ไทย" เป็นหลัก และมีเพียงส่วนน้อยมาก (<5%) ที่จะกดเปิดศึกษา "คอลัมน์ภาษาเดิม" การยัดข้อมูลภาษาเดิม 113MB (แม้บีบอัดแล้วเหลือ ~15-20MB) ลงใน HTML ของทุกหน้า (แนวทาง ก.) จะทำร้ายความเร็วในการโหลดของคนเน็ตช้าอย่างไร้ความปราณี
    *   **เรื่อง Google Index:** ข้อความภาษาเดิม (กรีก/ฮีบรู) และรหัสรูปผันต่าง ๆ ไม่ใช่คำที่คนไทยทั่วไปจะใช้ค้นหาบนกูเกิล สิ่งที่คนจะใช้พึ่งกูเกิลเสิร์ชหาคือคำแปลภาษาไทยทั่วไป เช่น "มัทธิว 2:1" หรือข้อความ "จงรักเพื่อนบ้าน" ดังนั้น การโหลดภาษาเดิมแบบ Dynamic ผ่านข้อ ข. จึงไม่ส่งผลเสียต่อเป้าหมายทางธุรกิจของเว็บเลย

#### **ทางเลือกที่ 4 ที่ดีกว่า (Hybrid Schema Compression + Local Client Caching)**
*   **สิ่งที่ผมวิเคราะห์/อนุมานเอง:** 
    1.  **ทำ JSON บดอัด (Schema Compression) รายบท (1,190 ไฟล์):** เปลี่ยนโครงสร้าง JSON ดิบเพื่อลดขนาดไฟล์ เช่น เปลี่ยนชื่อฟิลด์คีย์เป็นอักษรย่อตัวเดียว (เช่น เปลี่ยน `{"surface": "...", "lemma": "...", "morph": "..."}` เป็น `{"s": "...", "l": "...", "m": "..."}`) วิธีนี้จะช่วยรีดขนาดไฟล์ JSON รายบทให้เหลือเฉลี่ยบทละเพียง 15KB–40KB เท่านั้น 
    2.  **ทำระบบเก็บข้อมูลฝั่งผู้ใช้ (Client Caching):** เมื่อผู้ใช้เน็ตช้ากดเปิดบทใดบทหนึ่งแล้ว ให้ใช้ Service Worker หรือเขียนคำสั่ง Javascript ให้เก็บไฟล์ JSON นั้นลงใน `Cache Storage` หรือ `IndexedDB` ของมือถือผู้ใช้ เพื่อที่เมื่อพวกเขากลับมาอ่านบทเดิมซ้ำอีกครั้งในภายหลัง จะไม่ต้องเสียดาต้าอินเทอร์เน็ตในการโหลดใหม่อีกเลยแม้แต่กิโลไบต์เดียว

### ข้อ 2: การแสดงคำแปลสั้นภาษาอังกฤษ (English Gloss) แก่คนไทยสูงอายุ

*   **สิ่งที่ตำราพูดจริง (Jeff Johnson - Web Bloopers):**
    *   **ต้องพูดภาษาเดียวกับผู้ใช้และลบศัพท์เฉพาะทางระบบ (Insider Jargon & Speaking Geek):** ใน Chapter 6 (Blooper 42) ตำราเน้นย้ำว่า "ภาษาและคำศัพท์ของเว็บไซต์ต้องอิงตามภูมิหลังและภารกิจของผู้ใช้จริง ๆ ไม่ใช่ภาษาของระบบหรือโปรแกรมเมอร์" [6-8]. อินเทอร์เฟซที่ดีต้องช่วยให้ผู้ใช้รับรู้ข้อมูลได้ทันทีโดยไม่ต้องไปค้นหาความหมายต่อข้างนอก [9, 10].
    *   **ความซื่อสัตย์และหลีกเลี่ยงความคลุมเครือ:** ข้อมูลสินค้าหรือส่วนประกอบต่าง ๆ ต้องอธิบายอย่างซื่อตรงและเด่นชัดเพื่อให้ผู้ใช้แยกแยะจุดประสงค์ได้ถูกต้อง [6, 11, 12].
*   **สิ่งที่ผมวิเคราะห์/อนุมานเอง:**
    *   **ควรแสดงผล แต่ห้ามนำมาปะปนกับตัวบทหลักเด็ดขาด และต้องซ่อนไว้เริ่มต้น (Default collapsed):** คำแปลสั้นภาษาอังกฤษจาก MACULA มีไว้เพื่อประโยชน์ในการเทียบเคียงความหมายดั้งเดิมเชิงวิชาการสำหรับคนเรียนภาษาเดิม แต่สำหรับผู้สูงอายุไทยทั่วไปที่ไม่ได้ใช้ภาษาอังกฤษคล่องแคล่ว หากเราแสดงมันเด่นชัดขึ้นมาโดยไม่มีการคัดกรอง พวกเขาจะเข้าใจผิดว่าเป็นคำอธิบายส่วนตัวของผู้เขียนหรือตัวบทคัมภีร์หลัก
    *   **ข้อเสนอแนะเชิงดีไซน์:** ให้แสดงคำแปลภาษาอังกฤษนี้เฉพาะเมื่อผู้ใช้แตะ (Tap) ที่ตัวคำศัพท์ภาษาเดิมเพื่อดูความรู้เพิ่มเติมเท่านั้น โดยทำแถบหัวข้อคำอธิบายส่วนนี้ให้ต่างสีหรือต่างฟอนต์อย่างชัดเจน และใส่คำนำหน้ากำกับกำกวมชัดเป๊ะว่า: **"ความหมายภาษาอังกฤษดั้งเดิม (English Gloss): [คำศัพท์]"** เพื่อตอกย้ำให้คนสูงอายุรู้ว่านี่คือข้อมูลเชิงระบบที่มีไว้เทียบเคียง ไม่ใช่ข้อความพระคัมภีร์แปลไทยของเราเองครับ

*   **สิ่งที่ตำราพูดจริง:**
    *   **เกณฑ์ WCAG 2.2 SC 1.3.1 Info and Relationships:** โครงสร้างข้อมูลความสัมพันธ์ที่แสดงผลบนหน้าจอ จะต้องสามารถประมวลผลเชิงโปรแกรมได้จริง เพื่อรักษาระบบความสัมพันธ์ของตัวเอกสาร [1].
    *   **ความสมบูรณ์และซื่อตรงของข้อมูล (Missing Content & Consistency):** หลีกเลี่ยงความไม่สม่ำเสมอของเนื้อความ และต้องตรวจความพร้อมข้อมูลอย่างรอบคอบที่สุดก่อนนำเว็บขึ้นจริงเพื่อรักษาความน่าเชื่อถือ [6, 13, 14].
*   **สิ่งที่ผมวิเคราะห์/อนุมานเอง:**
    *(การวิเคราะห์โดยเน้นผลประโยชน์สูงสุดของผู้อ่านผู้เรียนพระคัมภีร์เป็นตัวตั้ง ไม่ใช่ความสะดวกของผู้เขียนโปรแกรม)*

#### **ก. สำหรับ 71 ข้อที่ภาษาไทยไม่มี แต่ต้นฉบับมี (เช่น สดุดี 3.1):**
*   **ห้ามซ่อนเด็ดขาด:** หากซ่อนไป คนที่ตั้งใจมาอ่านและตรวจความสัมพันธ์ภาษาเดิมของกรีก/ฮีบรู จะเข้าใจผิดว่าระบบมีบั๊ก ข้อมูลโหลดไม่ครบ หรือระบบลบเนื้อความบางส่วนทิ้ง
*   **ทางออกที่ดีที่สุด:** แสดงคำภาษาเดิมขึ้นมาให้ครบตามลำดับโครงสร้าง แต่ในสัดส่วนพื้นที่แปลไทยด้านข้าง ให้ระบายสีพื้นหลังเป็นแถบจาง ๆ และแสดงข้อความคำแนะนำชัดเจนว่า: **"(หัวเรื่องบทสดุดีเฉพาะในต้นฉบับภาษาเดิม — ไม่มีระบุข้อนี้ในพระคัมภีร์ฉบับแปลไทย TCV)"** วิธีนี้ทำให้โครงสร้างสารสนเทศครบถ้วนสมบูรณ์ และโปร่งใสต่อคนอ่านมากที่สุด

#### **ข. สำหรับ 3 ข้อที่แปลงแล้วข้อไทยทับซ้อนชี้ไปที่พิกัดต้นฉบับเดียวกัน (เช่น สดุดี 13.6):**
*   **ห้ามคัดลอกภาษาเดิมมาวางซ้ำ 2 รอบในแบบแยกส่วน:** หากคุณจับคู่แบบทื่อ ๆ แสดงเนื้อหาภาษาเดิมก้อนเดียวกันแยกเป็นสองข้อย่อยตามฉบับไทย ผู้อ่านจะเข้าใจผิดว่าในคัมภีร์ภาษาเดิมมีการเขียนประโยคซ้ำซ้อนกันสองครั้ง ซึ่งบิดเบือนตรรกะข้อเท็จจริงของคัมภีร์เดิม
*   **ทางออกที่ดีที่สุด:** ใช้ UI แบบ **"ผูกข้อมารวมกันชั่วคราว" (Unified Verse Container)** บนหน้าจอ เมื่อเลื่อนมาเจอจุดนี้ ให้แสดงรวบข้อไทยเป็น **"ข้อ 5–6"** ในบรรทัดเดียว แล้วแสดงตัวบทภาษาเดิมคู่กันเป็นก้อนเดียวด้านข้าง พร้อมแสดงเครื่องหมายอธิบายสั้น ๆ ว่าข้อทั้งสองถูกรวบอยู่ในข้อเดียวกันของต้นฉบับกรีก/ฮีบรู เพื่อรักษาความสอดคล้องเชิงความหมายจริง

### ข้อ 4: รายการ "ด่านตรวจอัตโนมัติ (Automated Gates)" 4 ด่านเพื่อค้ำประกันข้อมูล

เพื่อความรัดกุมสูงสุดในการป้องกันข้อความสูญหาย (ป้องกันการเกิดข้อหาย 133 ข้อประวัติศาสตร์ซ้ำรอย) และสามารถตรวจสอบได้จริงด้วยโค้ดคำสั่ง Node.js ตลอดสายพานการ Build (CI/CD Deploy pipeline):

```
[ ข้อมูลฐานข้อมูลดิบ ] ──> ( ด่านที่ 1: Checksum ) ──> ( ด่านที่ 2: Mapping ) ──> [ Nuxt Generate ] ──> ( ด่านที่ 3: HTML DOM ) ──> ( ด่านที่ 4: JSON Schema ) ──> [ Deploy GitHub ]
```

*   **สิ่งที่ตำราพูดจริง (Jeff Johnson / Morville):**
    *   ความผิดพลาดที่สร้างความสับสนแก่ผู้ใช้มักเกิดจาก "ความหละหลวมของกระบวนการตรวจสอบ" (Process blooper: failing to proofread) [6, 15].
    *   การใช้รหัสระบุเอกลักษณ์ (Unique IDs) ที่ชัดเจนในการเชื่อมโยง Chunk ข้อมูลจากต้นทาง (Source) สู่ปลายทาง (Destination) เป็นหัวใจสำคัญของงานระบบ [1, 3, 16-18].
*   **รายการ 4 ด่านตรวจที่เขียนเป็นคำสั่งสคริปต์ Node.js รันจริงฝั่ง Server/Runner (ผมวิเคราะห์เชิงวิศวกรรม):**

#### **ด่านที่ 1: Database Checksum Gate (นับจำนวนคำต้นทาง)**
*   **แนวทางรันสคริปต์:** สคริปต์คำนวณ Checksum ยอดรวมคำดิบก่อนเริ่มวาดเพจ โดยต้องทำการตรวจสอบเงื่อนไขดังนี้:
    1.  ยอดคำกรีกและฮีบรูรวมในชุดข้อมูลดิบ MACULA ต้องได้ตรงตามตัวเลขตรึงที่ **613,652 คำพอดีเป๊ะ**
    2.  ยอดรวมบทต้องเท่ากับ **1,190 บท** และยอดเล่มเท่ากับ **66 เล่ม**
    *   *คำสั่งสคริปต์:* ตรวจด้วยเงื่อนไข `if (wordCount !== 613652) { throw new Error("คำขาดหายก่อนเจเนอเรต!"); }` ถ้าไม่ผ่าน ให้สั่ง `process.exit(1)` เพื่อทำลาย Pipeline ทันที

#### **ด่านที่ 2: Verse Translation Mapping Integrity Gate (ตรวจสอบก่อนเจเนอเรต)**
*   **แนวทางรันสคริปต์:** รันสคริปต์จำลอง (Simulated Matching) เพื่อพิสูจน์ระบบจับคู่ข้อ:
    1.  ตรวจสอบว่าเลขข้อฉบับไทย TCV และเลขข้อต้นฉบับ จับคู่ตรงกันจำนวน **23,142 ข้อ**
    2.  ตรวจสอบและระบุค่าพิกัดเฉพาะ (Hardcoded rules check) ว่าในตรรกะระบบ มีข้อยกเว้นพิเศษ 3 ข้อที่ชนกัน และ 71 ข้อที่ไม่มีไทยอยู่ครบถ้วนในแผนที่ข้อมูล
    3.  หากระบบตรวจสอบแล้วพบว่ายอดรวมข้อที่ได้ไม่ครบ **23,145 ข้อ** ให้หยุดเขียนไฟล์ทันที

#### **ด่านที่ 3: HTML DOM Post-Build Scanner (ตรวจเช็กหลัง Nuxt เจเนอเรตเสร็จ)**
*   **แนวทางรันสคริปต์:** รันสคริปต์สแกนเนอร์ที่เขียนด้วย `cheerio` หรือ `jsdom` เข้าไปลุยอ่านในโฟลเดอร์ของผลผลิต (Dist output) ทุกไฟล์:
    1.  เช็กว่าในหน้าอ่านมีไฟล์ HTML ครบถ้วนจำนวน 1,190 ไฟล์บท
    2.  ใช้ Regex หรือ DOM Selector นับคำศัพท์ที่เป็นคีย์ภาษาเดิมรวมของทุกหน้าว่าเมื่อรวมกันแล้วต้องได้ครบ **613,652 ปุ่มคีย์เวิร์ด**
    3.  ตรวจสอบว่าปุ่ม Inline ทั้งหมดมีคุณสมบัติ `aria-expanded="false"` และไม่ปรากฏค่าว่างเปล่า

#### **ด่านที่ 4: JSON Payload Schema Validator (ตรวจโครงสร้างไฟล์สวิตช์ภาษาเดิม)**
*   **แนวทางรันสคริปต์:** ก่อนปล่อยไฟล์ JSON บทสลับภาษาขึ้น GitHub Pages ให้สคริปต์รันตัวสแกน Schema ตรวจจับ JSON ทั้ง 1,190 ไฟล์:
    1.  เช็กว่าทุกอ็อบเจกต์ในอาร์เรย์ของแต่ละบทต้องประกอบไปด้วยโครงสร้าง 5 ฟิลด์หลักครบถ้วน
    2.  ทำการเช็กค่า `null` หรือ `undefined` ในช่อง morph code, Strong's ID, และคำแปลอังกฤษเพื่อตัดปัญหา "ข้อมูลพิการวิปริต" ไม่ให้ออกไปแสดงบนจอจริงของคนอ่านครับ
