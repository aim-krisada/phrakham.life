### ข้อ 1: ขนาดของที่สร้างออกมา และเพดานของ GitHub Pages

* **การเก็บข้อมูลเมื่อสร้างใหม่:**
  * **เก็บเฉพาะผลสุดท้ายครับ** ตัว GitHub Pages จะนำไฟล์ชุดล่าสุดไปทับชุดเก่าบนเซิร์ฟเวอร์เว็บเสมอ ขนาดพื้นที่บนเซิร์ฟเวอร์จะไม่โตขึ้นเรื่อย ๆ ตามจำนวนครั้งที่กดสร้าง ( Build)
  * *(ยกเว้นแต่คุณจะเอาไฟล์ที่สร้างเสร็จแล้วไป Commit ลง Git History เอง ซึ่งไม่ควรถือเป็นวิธีปฏิบัติที่ดี ให้ใช้ GitHub Actions สร้างแล้วปล่อยลงไปที่ระบบ Deploy โดยตรง)*

* **ขนาดรวมของไฟล์ HTML 1,189 หน้า:**
  * ตัวบทไทย 20 MB + โครงสร้าง HTML/JS Shell ของ Nuxt (เฉลี่ยหน้าละ 10–20 KB) รวมแล้วไฟล์ static ที่สร้างออกมาจะอยู่ที่ประมาณ **35 – 50 เมกะไบต์** เท่านั้น ถือว่าเล็กมากสำหรับเว็บทั้งเว็บ

* **เพดานของ GitHub Pages ที่ต้องระวัง:**
  * **ขนาดเว็บรวม (Site Size Limit):** เอกสารทางการของ GitHub ระบุไว้ที่ **ไม่เกิน 1 Gigabyte** (ซึ่ง 50 MB ของเราใช้ไปไม่ถึง 5%)
  * **แบนด์วิดท์ (Bandwidth Limit):** เอกสารระบุไว้ที่ **100 Gigabytes ต่อเดือน**
  * *(หมายเหตุ: ตัวเลข 1 GB และ 100 GB เป็นตัวเลขซอฟต์ลิมิตตามเอกสารทางการของ GitHub แต่ไม่แน่ใจระบบการบล็อกจริงเมื่อเกินเกณฑ์ของ GitHub ในปัจจุบันว่าเด็ดขาดแค่ไหน)*

### ข้อ 2: เรื่องหน้าซ้ำ (Duplicate / Thin Content) ในสายตากูเกิล

กูเกิล **จะไม่มองว่าซ้ำ** ในแง่การลงโทษ (Penalty) เพราะโครงสร้างส่วนหัว/ท้าย (Layout) ที่เหมือนกันเป็นเรื่องปกติของเว็บประเภทบทความและระบบคลังข้อมูล แต่ **มีความเสี่ยงเรื่อง "Thin Content" ในบทที่สั้นมาก** เช่น สดุดี 117

**สิ่งที่ควรรอบคอบและทำไว้ป้องกัน:**

1. **ระบุ Canonical URL:** ใส่ `<link rel="canonical" href="...">` ใน `<head>` ของทุกหน้า เพื่อยืนยันกับกูเกิลว่าเป็นหน้าที่ตั้งใจให้มีอยู่จริง
2. **ใช้ Structured Data (Schema.org):** ฝัง JSON-LD ประเภท `Article` หรือ `Book` / `Chapter` บอกกูเกิลให้ชัดว่าหน้านี้คือ "บทที่เท่าไหร่ ของหนังสือเล่มไหน" เพื่อให้กูเกิลเข้าใจบริบทว่าทำไมเนื้อหาถึงมีแค่นั้น
3. **ระบบนำทางบริบท (Internal Linking):** มีปุ่ม "บทก่อนหน้า / บทถัดไป" และ ลิงก์ย้อนกลับไป "หน้าเล่ม" (เช่น หน้าเล่มสดุดี) กูเกิลจะมองเห็นโครงสร้างต้นไม้ที่สมบูรณ์ และเข้าใจว่าบทสั้น ๆ นั้นเป็นส่วนหนึ่งของคลังข้อมูลใหญ่

### ข้อ 3: การเก็บข้อมูลต้นทาง (Git LFS บีบก้อนเดียว VS JSON แยก 1,189 ไฟล์)

**คำตอบ: การแยกเป็น JSON 1,189 ไฟล์ (ไม่บีบ ไม่ใช้ LFS) ดีกว่ามหาศาลสำหรับระยะยาวและการทำงานเป็นทีม**

* **เหตุผล:**
  1. **การตรวจประวัติแก้ไข (Git Diff):** ไฟล์บีบก้อนเดียวใน Git LFS จะมองไม่เห็นเลยว่าใครแก้คำไหน บรรทัดไหน ในระบบ Git มันจะเห็นเป็นแค่ไบนารีเปลี่ยนไปทั้งก้อน ส่วนไฟล์ JSON แยกบท เมื่อมีคนแก้คำผิดใน "สดุดี 23" ระบบจะแสดงให้เห็นชัดเจนใน Pull Request ว่า *เปลี่ยนจากคำไหนเป็นคำไหน ในบรรทัดไหน*
  2. **การทำงานร่วมกันและชนกันของโค้ด (Merge Conflict):** ถ้าคนสองคนแก้คำผิดพร้อมกัน คนละเล่ม คนละบท
     * แบบก้อนเดียว LFS: โค้ดจะชนกันทำลายล้าง (Conflict) รวมโค้ดไม่ได้ ต้องเลือกของคนใดคนหนึ่ง
     * แบบแยกไฟล์: Merge ผ่านได้สบายเพราะแก้กันคนละไฟล์
  3. **ขนาดรวม 34 เมกะไบต์ ไม่จำเป็นต้องใช้ Git LFS:** Git ปกติรับไฟล์ข้อความขนาดรวม 34 MB ได้สบายมากแบบไม่มีปัญหาประสิทธิภาพ ไม่จำเป็นต้องเพิ่มความซับซ้อนด้วย Git LFS เลยครับ

**สรุปข้อ 3:** ใช้ไฟล์ **JSON แยกรายบท 1,189 ไฟล์แบบ Plain Text** เป็น Source ใน Git คือทางเลือกมาตรฐานสถาปัตยกรรมข้อมูลที่ดีที่สุดครับ
