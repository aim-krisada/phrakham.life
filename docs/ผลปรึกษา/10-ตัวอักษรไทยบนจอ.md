## 1. เลขข้อ ตัวยกหรือในบรรทัด

**คุณถูก และคำเตือนเดิมผิด** ตัวยก (superscript) **ไม่ได้ชนกับสระบนหรือวรรณยุกต์ของภาษาไทย** เลย ผมวัดด้วยพิกเซลจริงทุกฟอนต์ ทุกขนาด ทุกระยะบรรทัด — ไม่มีการชนแม้แต่กรณีเดียว

**หลักฐานที่ชี้ขาดที่สุด:** ผมวัดระยะห่างของ "หมึก" จริง ระหว่างสระล่างของบรรทัดบน (ปู่ ครู่ ผู้) กับสิ่งที่อยู่บนสุดของบรรทัดล่าง ที่ 18px:

| ฟอนต์ | lh | ตัวอักษรไทยธรรมดา `ที่` | `<sup>` ค่าเริ่มต้น | ตัวยกปรับแล้ว |
|---|---|---|---|---|
| Noto Sans Thai | 1.5 | **4.00 px** | 7.50 px | 7.00 px |
| Sarabun | 1.5 | **0.00 px (ชนพอดี)** | 6.25 px | 5.50 px |
| Sarabun | 1.75 | **4.50 px** | 11.25 px | 10.50 px |
| IBM Plex Sans Thai | 1.5 | **2.75 px** | 7.25 px | 5.75 px |
| Noto Serif Thai | 1.5 | **3.00 px** | 8.00 px | 6.50 px |

อ่านตารางนี้แบบนี้: **ตัวเลขตัวยกอยู่ "ต่ำกว่า" ยอดของสระ/วรรณยุกต์ไทยเสมอ** เพราะเลขอารบิกตัวยกสูงจากเส้นฐานประมาณ 17 px ขณะที่ `เปื้อน ที่ ตั้ง` สูง 19–20 px ตัวที่เฉียดบรรทัดบนคือ **ตัวหนังสือไทยเอง ไม่ใช่เลขข้อ** ถ้าตัวยกจะชน แปลว่าข้อความไทยธรรมดาชนไปก่อนแล้ว

**แต่มีปัญหาจริงอีกเรื่อง และมันร้ายกว่า — บรรทัดไม่เท่ากัน**

`<sup>` ค่าเริ่มต้นของเบราว์เซอร์ (`font-size:smaller` + `vertical-align:super`) **ดันกล่องบรรทัดให้สูงขึ้น ทุกบรรทัดที่มีเลขข้อ** และเกิดขึ้นที่ **ทุกค่า line-height** ไม่ใช่เฉพาะตอนบีบแน่น เพราะ `line-height` เป็นตัวเลขไร้หน่วยที่ถ่ายทอดลงไปที่ `<sup>` ด้วย กล่องของมันจึงโตตามและโผล่พ้นกล่องบรรทัดเสมอ

วัดที่ 18px Noto Sans Thai (ระยะห่างระหว่างบรรทัด px):

| line-height | `<sup>` ค่าเริ่มต้น | ตัวยกปรับแล้ว |
|---|---|---|
| 1.2 | 25.6 / 25.6 / 21.6 / 25.6 / 21.6 … **ต่างกัน 4.01** | 21.59 ทุกบรรทัด — **ต่างกัน 0.01** |
| 1.5 | 30 / 30 / 27 / 30 / 27 … **ต่างกัน 3.00** | 27.0 ทุกบรรทัด — **0.00** |
| 1.75 | 34.5 / 34.5 / 31.5 … **ต่างกัน 3.00** | 31.5 ทุกบรรทัด — **0.00** |
| 2.0 | 39 / 39 / 36 … **ต่างกัน 3.00** | 36.0 ทุกบรรทัด — **0.00** |

คือบรรทัดที่มีเลขข้อจะห่างกว่าบรรทัดปกติราว 9–19% ทำให้หน้าอ่านดู "กระตุก" เป็นระยะ ๆ

**ดูภาพ `02-uneven-lines-proof.png`** — เส้นแดงคือตำแหน่งที่บรรทัดควรอยู่ (ห่างเท่ากันเป๊ะ) คอลัมน์ซ้าย (`<sup>` ค่าเริ่มต้น) ข้อความค่อย ๆ ลอยหนีเส้นลงไปเรื่อย ๆ คอลัมน์กลางกับขวาเกาะเส้นสนิททั้งหน้า

**สิ่งที่ YouVersion ทำจริง** โค้ด CSS ของ SDK อย่างเป็นทางการของ YouVersion (เปิดดูได้ ผมอ่านไฟล์จริง) ใช้ **ตัวยกที่ปรับแล้ว ไม่ใช่ `vertical-align:super`**:

```css
.verse > .label, .fv, .yv-vlbl {
  display: inline;  font-size: 0.65em;  color: var(--yv-muted-foreground);
  line-height: 1em;  vertical-align: baseline;
  position: relative;  top: -0.2em;  white-space: nowrap;
}
```

`line-height:1em` + `vertical-align:baseline` + `top` คือกลไกเดียวกับที่ผมวัดแล้วได้ค่าความไม่เท่ากัน = 0 พอดี และผมยังพบว่าเว็บ/แอปพระคัมภีร์โอเพนซอร์สอื่นอีกหลายตัวก็ใช้ตัวยกเช่นกัน (บางตัวใช้ `vertical-align:super` ตรง ๆ ซึ่งมีบั๊กบรรทัดไม่เท่ากันแบบเดียวกัน) — **แนวปฏิบัติกระแสหลักคือตัวยก ไม่ใช่ตัวเลขในบรรทัด**

**คำแนะนำ (มั่นใจสูง)** ใช้เลขข้อแบบ **ตัวยก** ตามที่คุณเคยทำ แต่อย่าปล่อย `<sup>` ตามค่าเริ่มต้น ให้กำหนดเอง:

```css
.verse-num {
  font-size: .72em;      /* หรือ .65em แบบ YouVersion */
  line-height: 0;        /* กุญแจสำคัญ: กันไม่ให้ดันกล่องบรรทัด */
  vertical-align: baseline;
  position: relative; top: -.45em;
  white-space: nowrap;   /* เลขข้อไม่หลุดจากคำแรก */
  color: <สีเทาที่ผ่าน 4.5:1>;
  font-weight: 600;
}
```
ตามด้วย `&nbsp;` หลังตัวเลข (YouVersion ก็ทำแบบนี้)

ผมทดสอบ 5 แบบข้ามฟอนต์และ line-height — แบบ B (YouVersion), C (ด้านบน), E (ในบรรทัด + `line-height:0`) ได้ความไม่เท่ากัน 0.00–0.01 px ทั้งหมด ส่วน A (`<sup>` ค่าเริ่มต้น) **ล้มเหลวทุกกรณี** และแบบ D (ในบรรทัดหนาเทาโดยไม่ใส่ `line-height:0`) ยัง **ล้มเหลวกับ Sarabun** (ต่างกัน 1.74 px) — แปลว่าประเด็นแท้จริงไม่ใช่ "ตัวยก vs ในบรรทัด" แต่คือ **"กล่องของตัวเลขต้องไม่ไปแตะกล่องบรรทัด"** ต่างหาก

**อะไรจะทำให้ผมเปลี่ยนใจ:** ถ้าคุณจะใช้ฟอนต์ไทยที่ผมทดสอบไม่ได้ (Leelawadee UI, Tahoma — เครื่อง Windows ไทยได้สองตัวนี้ ผมโหลดมาไม่ได้) แล้ววัดพบว่าเลขตัวยกในฟอนต์นั้นสูงเกินยอดสระบน หรือถ้ามีผู้ใช้สูงอายุจริงบอกว่าอ่านเลขตัวยกไม่ออกเพราะเล็กเกินไป (คนละเรื่องกับการชน และเป็นเหตุผลที่ดีที่จะเลือก `.72em` แทน `.65em`)

## 2. ขนาดตัวอักษร

**เอกสารวิชาการเฉพาะภาษาไทยเรื่องขนาดขั้นต่ำบนจอ — บางมาก** ที่ค้นเจอเป็นงานเกี่ยวกับฉลากยาและสิ่งพิมพ์ ไม่ใช่จอ และผมเปิดอ่านตัวเต็มไม่ได้ (พร็อกซีบล็อก) จึงบอกตรง ๆ ว่า **ไม่มีตัวเลข "ขนาดขั้นต่ำสำหรับไทยบนจอ" ที่อ้างอิงได้จริง** ผมจะไม่แต่งตัวเลขขึ้นมา

สิ่งที่ผมทำได้คือ **วัดเอง** ดูภาพ `07-loops-small-sizes.png` — ผมเรียงคู่ตัวอักษรที่สับสนง่าย (ก/ถ/ภ, ค/ด/ต, พ/ม, ข/ช) ที่ 12–24px ทุกฟอนต์ ผลที่เห็นด้วยตา:
- **ที่ 12–14px หัวตัวอักษรเริ่มตัน** ก กับ ถ แยกยากขึ้นชัดเจน
- **ตั้งแต่ 16px ขึ้นไปหัวเปิดชัด** ทุกฟอนต์มีหัว
- ฟอนต์ไม่มีหัว (Kanit, Prompt) ไม่มีหัวให้ตันอยู่แล้ว แต่ก็ไม่มีตัวช่วยแยก ก/ถ เช่นกัน — **สำหรับผู้อ่านสูงอายุ ควรใช้ฟอนต์มีหัว** (Noto Sans Thai, Sarabun, IBM Plex Sans Thai, Noto Sans Thai Looped)

หลักฐานภายนอกที่ใช้ได้ (แต่ไม่ได้ยืนยันตัวเต็ม):
- งานทบทวนวรรณกรรมอย่างเป็นระบบใน Frontiers in Psychology (2022) เรื่องขนาดตัวอักษรสำหรับผู้สูงอายุบนมือถือ — สรุปว่า **18pt อ่านเร็วกว่าและเข้าใจดีกว่า 14 และ 16pt อย่างมีนัยสำคัญ และผู้สูงอายุกว่าครึ่งเลือก 18pt**
- **YouVersion SDK ตั้งค่าเริ่มต้นไว้ที่ 20px** (`--yv-reader-font-size: 20px`) — อันนี้ผมอ่านไฟล์จริง ยืนยันได้

**คำแนะนำ: 4 ระดับ ค่าเริ่มต้นคือระดับที่ 1**

| ระดับ | ตัวคูณ | ขนาดจริง (เมื่อเบราว์เซอร์ตั้ง 16px) |
|---|---|---|
| 1 · ปกติ **(ค่าเริ่มต้น)** | ×1.00 | **19px** |
| 2 · ใหญ่ | ×1.15 | 22px |
| 3 · ใหญ่มาก | ×1.32 | 25px |
| 4 · ใหญ่ที่สุด | ×1.52 | 29px |

```css
.reading { font-size: calc(1.1875rem * var(--fs, 1)); }
```
`1.1875rem` = 19px เมื่อผู้ใช้ไม่ได้แก้อะไร และ **เลื่อนตามการตั้งค่าฟอนต์ของเบราว์เซอร์ผู้ใช้เสมอ** ตามที่คุณตั้งใจไว้ ตัวคูณไม่เคยเขียนทับค่าสัมบูรณ์

**ทำไมไม่มีระดับเล็กกว่า 19px:** ผู้อ่านที่อยากได้เล็กกว่านี้ตั้งค่าที่เบราว์เซอร์เองได้อยู่แล้ว (และคุณเคารพค่านั้นอยู่) ส่วนกลุ่มเป้าหมายคือผู้สูงอายุ ปุ่มควรเน้นทางใหญ่ ถ้าอยากได้ 5 ระดับจริง ๆ ให้เติม ×0.87 (≈16.5px) ไว้ล่างสุด — อย่าต่ำกว่านั้น เพราะหัวตัวอักษรเริ่มตัน

**ภาพ:** `05-sizes-16-28.png` (16/18/20/24/28px บนคอลัมน์กว้างเท่าจอมือถือจริง 358px), `07-loops-small-sizes.png`, และหน้าจริงบนมือถือ 390px ทั้ง 4 ระดับ: `10-phone-step-17px.png`, `10-phone-step-19px.png`, `10-phone-step-22px.png`, `10-phone-step-26px.png`

## 3. ระยะห่างบรรทัดและความกว้าง

**ข้ออ้างว่า "ไทยต้องการระยะบรรทัดมากกว่าฝรั่ง" — จริง และมีแหล่งอ้างอิงระดับ W3C**

Richard Ishida (บรรณาธิการ i18n ของ W3C) เขียนไว้ใน Thai Orthography Notes หัวข้อ *Baselines, line height, etc.* ผมอ่านต้นฉบับแล้ว ข้อความตรงตัว:

> "Thai places vowel and tone marks above base characters, one above the other, and can also add combining characters below the line. The complexity of these marks means that **the vertical resolution needed for clearly readable Thai text is higher than for English**, or most Latin text. In addition, **Thai tends to adds more interline spacing than Latin text does.**"
>
> "The basic height of Thai letters is typically around the Latin x-height, however **extenders and combining marks reach well beyond the Latin ascenders and descenders, creating a need for larger line spacing.**"

**ข้อควรระวังที่ต้องบอกตรง ๆ:** เอกสารนี้บอกว่า "ต้องมากกว่า" แต่ **ไม่ได้ให้ตัวเลข** และหน้า W3C Thai Script Resources (SEALREQ) ที่คุณอาจคาดว่ามีตัวเลข ผมดึงมาอ่านทั้งหน้าแล้ว — **เป็นหน้าดัชนีลิงก์ล้วน ไม่มีตัวเลข line-height และไม่มีคำว่า superscript แม้แต่คำเดียว** ส่วนตัวเลข "1.55" ที่โผล่ในผลค้นหา ผมสาวกลับไปหาแหล่งที่มาที่ระบุชื่อได้ไม่เจอ — **อย่าเชื่อตัวเลขนั้น**

**เพราะฉะนั้นผมวัดเอง** ระยะห่างหมึกจริงระหว่างสระล่างบรรทัดบนกับสระ/วรรณยุกต์บนบรรทัดล่าง ที่ 18px (**ค่าติดลบ = หมึกซ้อนทับกันจริง**):

| line-height | 1.30 | 1.40 | **1.50** | 1.60 | 1.70 | **1.75** | 1.90 | 2.00 |
|---|---|---|---|---|---|---|---|---|
| Noto Sans Thai | 0.3 | 2.3 | 4.3 | 6.3 | 8.3 | 9.3 | 11.3 | 13.3 |
| **Sarabun** | **−5.0** | **−3.0** | **−1.0** | 1.0 | 3.0 | 4.0 | 6.0 | 8.0 |
| IBM Plex Sans Thai | **−2.0** | 0.0 | 2.0 | 4.0 | 6.0 | 7.0 | 9.0 | 11.0 |
| Noto Sans Thai Looped | **−2.3** | 0.0 | 1.5 | 3.5 | 5.5 | 6.5 | 8.5 | 10.5 |
| Noto Serif Thai | 0.0 | 1.5 | 3.5 | 5.5 | 7.5 | 8.5 | 10.5 | 12.5 |
| Loma | −0.8 | 1.3 | 3.3 | 5.3 | 7.3 | 8.3 | 10.3 | 12.3 |

ข้อสรุปสำคัญที่สุดในตารางนี้: **ที่ line-height 1.5 ซึ่งเป็นค่าที่ WCAG 1.4.12 ใช้ทดสอบ ฟอนต์ Sarabun (ฟอนต์ไทยยอดนิยมที่สุดตัวหนึ่ง) มีหมึกซ้อนทับกันจริง −1.0 px** ดังนั้น **1.5 คือพื้นขั้นต่ำที่ต้องไม่พัง ไม่ใช่ค่าที่ควรใช้**

**ตัวบทของ WCAG 2.2 SC 1.4.12 Text Spacing (AA)** — ผมดึงข้อความบรรทัดฐานมาตรงตัว:

> "In content implemented using markup languages that support the following text style properties, **no loss of content or functionality occurs** by setting all of the following and by changing no other style property:
> • **Line height (line spacing) to at least 1.5 times the font size;**
> • Spacing following paragraphs to at least 2 times the font size;
> • Letter spacing (tracking) to at least 0.12 times the font size;
> • Word spacing to at least 0.16 times the font size."
>
> หมายเหตุในตัวบท: "Content is **not required to use** these text spacing values. The requirement is to ensure that **when a user overrides** the authored text spacing, content or functionality is not lost."
>
> และหมายเหตุที่ตรงกับกรณีเรามาก: "Writing systems for some languages use different text spacing settings… **Authors are encouraged to follow locally available guidance for improving readability and legibility of text in their writing system.**"

ผมทดสอบจริงแล้ว: หน้าที่ใช้ 19px / lh 1.9 เมื่อถูกบังคับด้วยค่า WCAG ทั้ง 4 ข้อ **ไม่มีเนื้อหาหาย ไม่มีการเลื่อนแนวนอน** ทั้งที่จอ 390px และ 320px (scrollWidth = clientWidth เป๊ะทั้งคู่) ดูภาพ `04-wcag-1412-stress-390.png` และ `04-wcag-1412-stress-320.png`

**คำแนะนำ line-height ต่อระดับขนาด**

| ระดับ | ขนาด | line-height | ระยะหมึกที่ได้ (Sarabun กรณีแย่สุด) |
|---|---|---|---|
| 1 | 19px | **1.90** | ≈6.3 px |
| 2 | 22px | **1.85** | ≈6.6 px |
| 3 | 25px | **1.80** | ≈6.9 px |
| 4 | 29px | **1.75** | ≈6.4 px |

เหตุผลที่ค่าลดลงเมื่อตัวโตขึ้น: ระยะหมึกเป็น px โตตามขนาดฟอนต์อยู่แล้ว ถ้าคง 1.9 ไว้ที่ 29px จะเว่อร์และทำให้ต้องเลื่อนหน้าจอยาวมาก การไล่ลงแบบนี้ทำให้ **ช่องว่างที่ตาเห็นคงที่ประมาณ 6–7 px ทุกระดับ** และทุกค่ายังสูงกว่า 1.5 ของ WCAG อย่างสบาย

| 36em | 648 | ≈52 |
| 46em | 828 | ≈58 |

(ค่าที่ 36–40em แกว่งเพราะตำแหน่งตัดคำ ให้ดูเป็นแนวโน้ม)

**แนะนำ `max-width: 34em`** ≈47 อักขระไทย ต่ำกว่ากรอบ 45–75 ตัวอักษรของฝรั่งเล็กน้อย ซึ่งเหมาะสม เพราะอักขระไทย 1 ตัวกว้างกว่าและ "หนัก" กว่าอักษรละติน 1 ตัว (ไทยเฉลี่ย ≈0.67em ต่อตัว) เทียบเคียง: **YouVersion ตั้ง `max-width: 65ch`** ซึ่งเป็นกรอบละติน

จุดสำคัญ: **ต้องใช้หน่วย `em` ไม่ใช่ `px`** เพราะเมื่อผู้ใช้กดขยายตัวอักษร ความกว้างจะขยายตามเอง จำนวนตัวอักษรต่อบรรทัดคงที่ — ซึ่งเป็นพฤติกรรมที่ถูกต้อง และแปลว่า **ความกว้างไม่ต้องมีปุ่มของมันเอง** บนมือถือ 390px เรื่องนี้ไม่มีผลอยู่แล้วเพราะจอบังคับความกว้างให้เอง

## 4. ปุ่มเดียวหรือหลายปุ่ม

**ปุ่มเดียว** — ควบคุมขนาดตัวอักษรอย่างเดียว แล้วให้ระยะบรรทัดกับความกว้างขยับตามเองโดยอัตโนมัติ

เหตุผล:
1. **ผู้อ่านไม่มีทางรู้ว่าควรตั้ง line-height เท่าไร** ถ้าเปิดให้ตั้งเอง เขาจะตั้งเป็น 1.4 แล้วสระกับวรรณยุกต์จะทับกันจริง ๆ (ดูตารางข้างบน) เท่ากับเรายื่นปืนให้เขายิงเท้าตัวเอง
2. **ความกว้างไม่ต้องมีปุ่มอยู่แล้ว** ถ้าเขียน `max-width` เป็น `em` มันตามขนาดตัวอักษรไปเอง 100%
3. **KISS** ปุ่มเดียวคือ 2 ปุ่ม ก–/ก+ หรือปุ่มเลือก 4 ช่อง เก็บค่าเดียวใน localStorage ทดสอบ WCAG ได้ 4 สถานะ ไม่ใช่ 4×4×4

โครงสร้าง:
```css
.reading{
  --fs: 1; --lh: 1.90;
  font-size: calc(1.1875rem * var(--fs));
  line-height: var(--lh);
  max-width: 34em;
}
.reading[data-size="2"]{ --fs:1.15; --lh:1.85 }
.reading[data-size="3"]{ --fs:1.32; --lh:1.80 }
.reading[data-size="4"]{ --fs:1.52; --lh:1.75 }
```
ปุ่มแตะแค่ `data-size` ค่าเดียว — เรื่องอื่นตามมาเอง

ข้อควรระวังด้าน WCAG: ปุ่มต้องเป็น `<button>` จริง มีสถานะ `aria-pressed` และขนาดพื้นที่แตะ ≥24×24 CSS px ตาม SC 2.5.8 (แนะนำ 44×44 สำหรับผู้สูงอายุ)
