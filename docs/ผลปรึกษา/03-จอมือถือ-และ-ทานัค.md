## ก. จอมือถือและการวางของ

**1. `tabs.hidden = true` ไม่ทำงาน — แท็บพันธสัญญาค้างอยู่ทุกหน้าจอ · ความรุนแรง 3**
`.tabs{display:flex}` is an author rule; `[hidden]{display:none}` is only in the UA stylesheet, so the author rule wins. Compare `.scrim[hidden]`, `.drawer[hidden]`, `.modal[hidden]` — all three have explicit companion rules (lines 134, 140, 155); `.tabs` (line 178) does not. Result: `showChapters()`/`showVerses()` set `tabs.hidden = true` and nothing happens. On the chapter screen for สดุดี the user still sees "พันธสัญญาเดิม / พันธสัญญาใหม่" eating 44px + .6rem padding ≈ 54px of a 320px-wide phone, still tabbable, and tapping either one silently throws away the book they just chose. Fix: add `.tabs[hidden]{display:none}` (and do the same for every element you hide in JS that has an author `display`).

**2. งานหลักอยู่บนสุด ที่นิ้วโป้งเอื้อมยากที่สุด · ความรุนแรง 3**
Stacking the mobile column at 320px: header ≈ 64px → `main` padding-top 32px → wordmark 1.9rem×1.6 = 48.6 + 5.6 → lead (2 lines) 48.6 + 19.2 → pill 54 → `.pick-wide` 9.6 + 54 → chips end ≈ y 421. So **"เลือกหนังสือ บท ข้อ" is centred at y ≈ 308**. On a real 390×844 phone (~800px viewport) that is the top 38% of the screen, and **~380px below the chips is empty white — exactly the bottom-third comfort zone** that Hoober's reach maps identify as the only truly one-handed area. Fix: either bottom-anchor the search cluster on mobile (push it down with `margin-top:auto`), or accept the top position but make the book picker a bottom sheet so the thing people actually tap starts within thumb reach.

**3. ช่วง 360–520px คือหลุมที่โครงร่างนี้ไม่ได้แสดง · ความรุนแรง 3**
The wireframe shows only 320 and 1100, but the real breakpoint has to be computed. In desktop mode the pill holds three things. At 414px: `searchwrap` = 414 − 32 = 382, pill content 380. `.pick-btn` = 32 padding + 20 icon + 7.2 gap + "เลือกหนังสือ" (9 advance-bearing glyphs × ≈0.6em × 16px ≈ 86px) + 1 border ≈ **147px**. `.go-btn` = 32 padding + 20 icon + 6.4 gap + "ค้นหา" (4 × 0.6 × 16 ≈ 38) ≈ **97px**. Input left with 380 − 147 − 97 = 136px, minus its own 28.8px padding = **107px of typing space** — under 12 Thai characters. Working backwards, the input needs ≈200px to show "มัทธิว 2:1-2" plus a cursor, so the pill needs ≈444px plus 32px page padding ≈ **475–520px**. Fix: apply the `.pick-wide` treatment up to about **520px**, not just at 320px, and state that number in the real CSS.

**4. เลือกเสร็จแล้วไม่ได้พาไปอ่าน — ถูกส่งกลับเข้าช่องพิมพ์ พร้อมคีย์บอร์ดเด้ง · ความรุนแรง 3**
`pick()` (line 428) closes the modal, writes the reference into `#ref` and calls `.focus()`. On a phone that pops the keyboard, which covers roughly the bottom 45% of the screen — and the "ค้นหา" button the user now has to press is inside the pill at y ≈ 272, above the keyboard but only just. The user has already specified book + chapter + verse; asking for one more tap is a wasted step. The file itself notes the keyboard problem at line 481 for page load, then reintroduces it here. Same applies to the example chips (line 476). Fix: picking a chapter or verse should navigate straight to the passage; the text box is the alternative path, not the destination.

**5. ชื่อหนังสือยาวในตาราง 2 คอลัมน์ มีที่เหลือแค่ 9–27px และไม่มีทางหนี · ความรุนแรง 3**
Arithmetic at 320px: frame 320 − modal padding 2×8 = card **304px**; minus 2px border = 302; minus grid padding 2×14.4 = **273.2px**; 2 columns with a 6.4px gap → **133.4px per column**; minus button border 2 + padding 2×4.8 = **121.8px of text width**. "เฉลยธรรมบัญญัติ" has 12 advance-bearing glyphs (the ั and ิ are zero-width marks) at .9rem = 14.4px; at ≈0.55–0.65em that is **95–112px**. It fits, but with only 9–27px to spare. Now the failure modes: (a) it is a single Thai word with no space, so no line-breaker can split it; (b) `.grid button` has no `overflow-wrap`, no `text-overflow`, no `overflow:hidden`; (c) `repeat(2,1fr)` columns carry an implicit `min-width:auto`, so when min-content exceeds the share the **column grows and the grid scrolls sideways** inside the card. Triggers: the Tahoma/Leelawadee fallback (wider Thai than Noto Sans Thai — at 0.7em the string needs 121px, past the budget), Android's font-scale setting, or 200% zoom. At 200% zoom on a 390px phone the layout viewport is ~195px → cell text width drops to ≈**59px** against a ≈104px string — certain blow-out. Fix: below ~380px go to **one column** for books; add `overflow-wrap:anywhere` plus a two-line clamp on `.grid button`; and consider `font-size:.85rem` only for the OT grid.

**6. ช่องในตารางบนจอคอมพิวเตอร์ "แคบกว่า" บนมือถือ · ความรุนแรง 2**
`.modal-card` max-width 560px, 4 columns: (560 − 2 border − 28.8 padding − 3×6.4 gap) / 4 = **127.5px per column**, text width **115.9px** — narrower than the mobile 2-column cell's 121.8px. The longest name is therefore *more* likely to overflow on a 1100px desktop than on a 320px phone. Fix: on wide screens raise the modal to ~800px and use 5 columns → (800 − 2 − 28.8 − 25.6)/5 = **148.7px** per column, ≈137px of text — comfortable.

**7. ตารางไม่รีเซ็ตตำแหน่งเลื่อนเมื่อเปลี่ยนขั้น · ความรุนแรง 2**
`showChapters()` clears and refills `#bmGrid` but never sets `grid.scrollTop = 0`; `grid.focus()` on a `tabindex="-1"` container does not scroll it. Whether the browser clamps scrollTop between the `innerHTML=''` and the appends depends on whether layout is flushed, so this is browser-dependent rather than certain — which is itself the reason to fix it explicitly. Worst case is exactly the common case: สดุดี sits at row 10 of 20, so the user has scrolled ~500px to reach it, then lands part-way down a 150-chapter grid instead of at chapter 1. Fix: one line, `grid.scrollTop = 0`, in both `showChapters` and `showVerses`.

**8. ไม่มีสัญญาณว่าตารางเลื่อนได้ — หนังสือท้าย ๆ 8 เล่มหายไปเงียบ ๆ · ความรุนแรง 2**
39 books in 2 columns = 20 rows × (44 + 6.4) ≈ **1008px** of grid against a card of at most 640−16 = 624px on the wireframe frame. Roughly the last 8 books (นาฮูม → มาลาคี) are below the fold, and iOS overlay scrollbars are invisible until touched, so the card's hard bottom border reads as "the list ends here". Fix: a fade at the bottom edge, and size rows so a partial row peeks — the single most reliable scroll cue.

**9. กล่องกระโดดขึ้นลงระหว่างขั้น เพราะ `align-items:center` · ความรุนแรง 2**
The book step produces a near-full-height card; the chapter step for ยูดา (1 chapter) produces a card ~200px tall, vertically centred. So the ✕ and the "‹ หนังสือ" back button move several hundred pixels between two consecutive taps. Fix: on mobile pin the card to the bottom (a bottom sheet) or to the top with a fixed height — anything that keeps the header and the back control at a constant y. This also fixes finding 2, since a bottom sheet puts the whole picker in the thumb zone.

*Note in credit:* the scrolling itself is correct. `.grid` has `overflow:auto`, which sets its flex automatic minimum size to zero, so the grid — not the card — scrolls and the header/breadcrumb/tabs stay put. That is the right structure and worth keeping.

**10. ข้อความตัวอย่างในช่องพิมพ์ถูกตัดครึ่ง — ส่วนที่สอนรูปแบบหายไปทั้งหมด · ความรุนแรง 2**
At 320px: `searchwrap` = 320 − 24 = 296, pill content 294, `.go-btn` ≈ 97 → input box 197px, minus 28.8px padding = **168px of visible text**. The placeholder "พิมพ์ชื่อหนังสือ บท ข้อ เช่น มัทธิว 2:1-2" needs ≈285px. About **59%** shows; the user sees roughly "พิมพ์ชื่อหนังสือ บท ข้อ เช…" and **never sees "มัทธิว 2:1-2"**, which is the only part that teaches the format. Fix: shorten the placeholder to "เช่น มัทธิว 2:1-2" and move the instruction to a visible line above the field; and make "ค้นหา" icon-only on mobile (97px → 52px), returning 45px to the input.

**11. ลิ้นชักเมนู: ปิดยาก และใหญ่เกินของที่ใส่ · ความรุนแรง 2**
`min(86%,300px)` at 320px = **275px**, leaving a **45px scrim strip on the left edge** — the tap-to-dismiss target sits in the region reach maps rate hardest for a right thumb (top-left/left edge needs a regrip), while the ✕ is at the top-right corner (12–18% error region). The content is 5 links: drawer-head ≈63px + 5×48 = 240 → **303px used of ~800px**, two-thirds empty. Right-side drawer matched to a right-side menu button is the correct call and should stay; the size is not. Fix: for 5 items use a bottom sheet or a simple dropdown panel under the button, or keep the drawer but bottom-align the link list so it lands in the thumb zone.

**12. "ทั้งบท" ซ่อนอยู่ในช่องตัวเลขกว้าง 49.5px · ความรุนแรง 2**
Mobile number grid: (273.2 − 4×6.4)/5 = **49.5px per cell** — fine for digits, and comfortably over the 46px that Hoober's rage-tap data recommends for the lower screen. But `showVerses()` puts "ทั้งบท" as cell #1 of that same grid: 4 advance glyphs ≈35px + 9.6 padding + 2 border ≈ **46px in a 49.5px box**, zero slack, and the most likely action on the screen is dressed as verse number zero. Fix: give "อ่านทั้งบท" its own full-width button above the verse numbers.

**13. คำโปรยชื่อเว็บซ้ำสองที่ · ความรุนแรง 1**
`.brand` in the header and `.wordmark` in `main` say "พระคำ.ชีวิต" twice within 96px of each other. The wordmark alone costs 48.6 + 5.6 = **54px** of the scarcest space on the page. Fix on mobile: drop the large wordmark, keep the header brand, and let the tagline carry the identity.

**14. กด Enter บนคีย์บอร์ดมือถือแล้วไม่เกิดอะไร · ความรุนแรง 1**
The input is not inside a `<form>` and there is no Enter handler (`#goBtn` has no listener at all). Acceptable in a wireframe, but note it now: on a phone the keyboard's Go key is the natural submit, and without a form the user must dismiss the keyboard first. Fix in the real build: wrap the pill in `<form>` with a `submit` handler.

**15. องค์ประกอบจอคอมพิวเตอร์ · ความรุนแรง 1**
The 620px centred column on an 1100px canvas is the right call — Google-shaped, and it keeps the eye on one target. Two notes only: content ends around y ≈ 400 of a 640px min-height frame and far higher on a real 900px display, so the lower half is empty while the five sections (เล่าประสบการณ์, ความรู้ประกอบ, แหล่งข้อมูล, เพลง) get nothing but a 0.95rem link; and the 4-column book grid should widen as in finding 6. On a desktop there is also no reason for the picker to be a modal at all — a panel that opens in place would let the reader keep the page visible.

*Also in credit:* every interactive element uses `min-height`, never a fixed `height`. With Thai's stacked upper and lower marks at line-height 1.6 that is the decision that keeps 200% zoom and large system fonts from clipping text. Keep it as a rule.

## ข. โครงหน้าต่างเลือกหนังสือ + ทานัค

**7 · ที่อยู่ของตัวเลือก — segmented control เหนือตารางพันธสัญญาเดิม เห็นเฉพาะแท็บนั้น**
This is a change of *presentation* of the same 39 books, not a change of *content* — which is precisely the line that separates a segmented control from a tab (tabs swap what you are looking at; segmented controls re-sort, re-format or filter what is already there). A **third tab is the worst option**, and the arithmetic proves it independently of theory: three tabs across 273.2px with two 6.4px gaps gives 86.8px each, minus 2px border and ~12px UA button padding = **72.8px of text**, while "พันธสัญญาเดิม" needs 10 advance glyphs × ≈0.6em × 16px ≈ **96px**. A third tab breaks the two labels that currently work (at two tabs each label has 119.4px, comfortably over 96px). A third tab also asserts that Tanakh is a *third scripture* alongside OT and NT, which is factually wrong and will confuse exactly the readers with no church background. A **site-wide setting in the menu** is worse still: nobody will find it, and it creates an invisible mode, so a returning visitor meets a Bible in an order they do not remember choosing with no on-screen explanation. A **dropdown in the modal header** hides the options behind a tap for a binary choice, and the header at 320px is already 304px wide carrying a title plus a 44px ✕ — there is no room. The segmented control keeps both options permanently visible, costs one row, sits directly above the thing it changes, and vanishes on the NT tab where it is meaningless.

**8 · 39 เล่มเสมอ เปลี่ยนแค่ลำดับและการจัดหมวด ไม่ยุบเป็น 24**
Merging changes the *addressing scheme*, not just the sort order, and that is a much larger commitment than it looks. A merged "ซามูเอล" would need 55 chapters (31 + 24) — but every Thai Bible in print, every sermon, every cross-reference and every link the reader will ever encounter says "2 ซามูเอล 7", never "ซามูเอล 38". A user who taps chapter 38 gets a reference they cannot quote, cannot search, and cannot match to the book in their hand. The Twelve is worse: as one book it runs 67 continuous chapters from Hosea to Malachi, and nobody can find Jonah at "chapter 30-something". Re-sorting costs nothing and breaks nothing: the URL, the reference string and the chapter numbers stay identical in both modes, so links remain shareable across the setting — which also quietly answers question 11. State the trade honestly to the owner: this means the site never literally displays "24 เล่ม", so a visitor who came specifically for the 24-book count gets the structure but not the number. The compromise that recovers most of it without breaking addressing is a group sub-heading — "ซามูเอล (ฉบับยิวนับเป็นเล่มเดียว)" with the two existing tiles under it — communicating the structure in words while 1/2 stays intact.

**9 · จัดหมวดทั้งสองแบบ และจัดหมวดพันธสัญญาใหม่ด้วย — นี่คือกุญแจ**
Yes, and this is the move that dissolves the whole problem. If only the Tanakh view has headings, Tanakh reads as an exotic special case that needs explaining. If **both** OT arrangements carry group headings, the control stops meaning "normal Bible vs. Jewish Bible" and starts meaning "**two ways of grouping the same 39 books**" — a far easier idea for a reader with no background. Grouping also pays off independently on mobile: 39 undifferentiated tiles over 20 scroll-rows have no landmarks at all, and group headings give the reader a position sense while scrolling (with a sticky heading, an answer to "where am I?" at every scroll position). Counts check out in both arrangements: Christian 5 + 12 + 5 + 5 + 12 = 39; Tanakh as tiles 5 (Torah) + 21 (Nevi'im: Joshua, Judges, 1–2 Sam, 1–2 Kings, Isaiah, Jeremiah, Ezekiel, the Twelve) + 13 (Ketuvim, with Ezra and Nehemiah and 1–2 Chronicles kept separate) = 39. Extend the same treatment to the NT — พระกิตติคุณ 4 + กิจการ 1 + จดหมายของเปาโล 13 + จดหมายอื่น 8 + วิวรณ์ 1 = 27 — so grouping is simply how this picker works, everywhere.

**One research finding the owner must act on: there is no single "Tanakh order".** Torah and Nevi'im are stable, but Ketuvim varies by tradition. The Talmudic order (Bava Batra 14b–15a) is Ruth, Psalms, Job, Proverbs, Ecclesiastes, Song of Songs, Lamentations, Daniel, Esther, Ezra, Chronicles. The Tiberian Masoretic codices (Aleppo, Leningrad) put **Chronicles first**: Chronicles, Psalms, Job, Proverbs, Ruth, Song of Songs, Ecclesiastes, Lamentations, Esther, Daniel, Ezra. Modern printed Hebrew Bibles commonly differ again. You must pick one and name it on screen; "ทานัค" alone does not specify an order.

**10 · คำไทยที่เสนอ**

Control, shown only on the OT tab, caption above it:

> **ลำดับเล่ม**  ⟨ **แบบคริสเตียน** | **แบบยิว (ทานัค)** ⟩

One helper line under the control, changing with the selection:
- แบบคริสเตียน: "เรียงแบบพระคัมภีร์ไทยทั่วไป ปฐมกาล → มาลาคี"
- แบบยิว: "เรียงแบบที่ชาวยิวใช้ แบ่งเป็น 3 หมวด ปฐมกาล → พงศาวดาร"

"แบบยิว" carries the meaning for someone who has never heard the word Tanakh; "(ทานัค)" in parentheses lets the person who *does* know the word recognise it and find it by search. Never use "ทานัค" alone as the label.

Group headings — แบบคริสเตียน (plain Thai first, the church term in parentheses where it helps):
- **บทบัญญัติ · 5 เล่มแรก**
- **ประวัติศาสตร์**
- **บทกวีและคำสอน**
- **ผู้พูดแทนพระเจ้า เล่มยาว** (ผู้เผยพระวจนะใหญ่)
- **ผู้พูดแทนพระเจ้า เล่มสั้น** (ผู้เผยพระวจนะน้อย)

Spelling out ใหญ่/น้อย as ยาว/สั้น is not a liberty — length is exactly what the traditional terms mean, and "ใหญ่/น้อย" is routinely misread as importance.

Group headings — แบบยิว:
- **หมวดบทบัญญัติ (โตราห์)**
- **หมวดผู้พูดแทนพระเจ้า (เนวีอิม)**
- **หมวดข้อเขียน (เคทูวิม)**

Group headings — พันธสัญญาใหม่:
- **เรื่องราวของพระเยซู** (พระกิตติคุณ) · **กิจการ** · **จดหมายของเปาโล** · **จดหมายอื่น ๆ** · **วิวรณ์**

**11 · จำไว้ในเครื่อง ใช่ · กระทบพันธสัญญาใหม่ ไม่**
Persist it, but only in `localStorage` on that device, silently, and only on condition that the control is always visible in the picker — a remembered setting is acceptable exactly when it is never hidden. Do **not** put it in the URL and do not let it touch the reading page: because we chose not to merge books (question 8), "1 ซามูเอล 7" is identical in both modes, so every shared link works for every recipient regardless of their setting. That property is worth protecting and is the strongest practical argument for the no-merge decision. The New Testament is untouched — the Tanakh is the Hebrew Bible and has no New Testament, so the concept simply does not apply there. The control must therefore disappear entirely on the NT tab, not be greyed out; showing it disabled would imply it *could* apply. That requirement also independently rules out the header dropdown and the site-wide menu setting, both of which would imply the choice governs the whole site.

## ค. คำถามที่ต้องให้เจ้าของตัดสิน

1. **หมวดข้อเขียน (เคทูวิม) จะเรียงแบบไหน** — แบบทัลมุด (นางรูธ ขึ้นก่อน) / แบบต้นฉบับโบราณ (พงศาวดาร ขึ้นก่อน) / แบบพระคัมภีร์ฮีบรูที่พิมพ์ขายทุกวันนี้ (สดุดี ขึ้นก่อน) — ต้องเลือกหนึ่งอย่าง เพราะ "ลำดับแบบทานัค" ไม่ได้มีแบบเดียว
2. **แสดง 39 เล่มเสมอ แค่เรียงใหม่** หรือ **ยุบเหลือ 24 เล่ม** (ซามูเอลเล่มเดียว 55 บท)
3. **ใช้คำว่า "ทานัค" บนหน้าจอไหม** — ใช้ "แบบยิว (ทานัค)" หรือ "แบบยิว" เฉย ๆ
4. **จัดหมวดให้ทุกแบบ** (ทั้งคริสเตียน ทั้งยิว ทั้งพันธสัญญาใหม่) หรือ **จัดหมวดเฉพาะแบบยิว**
5. **ใช้คำแบบคริสตจักร ("ผู้เผยพระวจนะ")** หรือ **คำชาวบ้าน ("ผู้พูดแทนพระเจ้า")** เป็นหัวข้อหมวด
6. **เลือกครบ หนังสือ–บท–ข้อ แล้วพาไปอ่านทันที** หรือ **กลับมาเติมในช่องพิมพ์ก่อน**
7. **จำการตั้งค่าลำดับเล่มไว้ในเครื่องผู้ใช้ไหม** — จำ หรือ เริ่มที่แบบคริสเตียนทุกครั้ง
8. **หน้าต่างเลือกหนังสือบนมือถือ** — ทำเป็นแผ่นเลื่อนขึ้นจากขอบล่าง หรือ คงเป็นกล่องกลางจอแบบนี้
9. **สลับเป็นหน้าตาแบบมือถือที่ความกว้างเท่าไร** — ตามที่คำนวณได้ควรราว 520px ไม่ใช่ 320px ยืนยันได้ไหม
10. **บนมือถือ ตัดคำโปรยชื่อเว็บตัวใหญ่กลางจอออกไหม** — ตัดออกเพื่อเอาที่ 54px หรือ เก็บไว้
