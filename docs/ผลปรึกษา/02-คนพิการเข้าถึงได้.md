# ส่วน ก · บั๊กจริงในโค้ด (ต้องแก้ ไม่ว่าดีไซน์จะเปลี่ยนหรือไม่)

### ก1. `showBooks()` ไม่คืนโฟกัส → โฟกัสหลุดออกไปที่ `<body>` นอกไดอะล็อกที่ประกาศ `aria-modal="true"`
- (ข) **ปิดกั้น**
- (ค) APG *Dialog (Modal)* — "modal dialogs contain their tab sequence. That is, Tab and Shift + Tab do not move focus outside the dialog"; WCAG 2.2 SC 2.4.3 Focus Order
- (ง) บรรทัด 391–399 เทียบกับ 410 และ 426:
```js
function showBooks(){
    title.textContent = 'เลือกหนังสือ';
    crumb.innerHTML = ''; tabs.hidden = false;      // ← ทำลายปุ่ม '‹ หนังสือ' ที่กำลังโฟกัสอยู่
    ...
}                                                   // ← ไม่มี grid.focus();
```
  `showChapters` (410) และ `showVerses` (426) มี `grid.focus();` ปิดท้าย แต่ `showBooks` ไม่มี
- (จ) เส้นทางที่เกิดจริง: เปิดหน้าต่าง → กดหนังสือ → กดปุ่มเบรดครัมบ์ `‹ หนังสือ` → `crumb.innerHTML=''` ลบปุ่มที่โฟกัสอยู่ทิ้ง → เบราว์เซอร์คืนโฟกัสให้ `<body>` ซึ่งอยู่นอก `#bookModal` ผลลัพธ์ต่อเนื่อง: (1) กด Tab ต่อ ตัวดัก `trap` ผูกอยู่กับ `modal` (บรรทัด 453) จึงไม่มีวันได้รับ event ที่ target เป็น `<body>` (body เป็น ancestor ไม่ใช่ descendant) โฟกัสจึงวิ่งไปที่แถบเครื่องมือ/ลิงก์ header/ช่อง `#ref` ทั้งที่หน้าต่างยังเปิด (2) เพราะประกาศ `aria-modal="true"` ไว้ ผู้ใช้ NVDA/VoiceOver อาจไม่ได้ยินอะไรเลยจากบริเวณที่โฟกัสไปตก = ทางตัน
- **แก้:** เติม `grid.focus();` ท้าย `showBooks()` และแยกเป็นฟังก์ชันเดียวกันทั้งสามขั้น เพิ่มเติม: ย้าย `trap` ไปฟังที่ `document` ตอนไดอะล็อกเปิด (ดู ก6) และตั้ง `inert` ให้พื้นหลัง (ดู ข1) เพื่อกันกรณีที่โฟกัสหลุดด้วยเหตุอื่น

### ก2. `tabs.hidden = true` ไม่ได้ซ่อนอะไรเลย — CSS `.tabs{display:flex}` ชนะ UA rule `[hidden]{display:none}`
- (ข) **หนัก**
- (ค) WCAG 2.2 SC 4.1.2 Name, Role, Value; SC 1.3.1 Info and Relationships; APG *Tabs*
- (ง) บรรทัด 178 กับ 402/414:
```css
.tabs{display:flex;gap:.4rem;padding:0 .9rem .6rem}   /* บรรทัด 178 — ไม่มี .tabs[hidden]{display:none} */
```
```js
tabs.hidden = true;   // บรรทัด 402 (showChapters) และ 414 (showVerses)
```
  ไฟล์นี้เขียน override ครบสำหรับสามตัวอื่น — `.scrim[hidden]` (134), `.drawer[hidden]` (140), `.modal[hidden]` (155) — แต่ **ลืม `.tabs`**
- (จ) ประกาศของ author ชนะ UA stylesheet เสมอตามลำดับ cascade origin ดังนั้น `display:flex` ทับ `[hidden]{display:none}` ผลคือ tablist ยังแสดงอยู่และยังอยู่ใน tab order ตลอดขั้นเลือกบท/เลือกข้อ พร้อม `aria-selected="true"` บนแท็บที่พาเนลไม่ได้แสดงเนื้อหาของมันแล้ว ผู้ใช้สกรีนรีดเดอร์จะเจอ tab ที่โกหก
- **แก้:** เพิ่ม `.tabs[hidden]{display:none}` และดูข้อ ก3 ด้วย — แต่ทางที่ถูกกว่าคืออย่าใช้ Tabs pattern สำหรับ wizard สามขั้นนี้ตั้งแต่แรก (ดู ข3)

### ก3. ตัวจัดการ ArrowLeft/ArrowRight อ่าน `document.activeElement` หลังเรียก `focus()` แล้ว → โฟกัสแท็บหนึ่ง แต่สั่ง click อีกแท็บหนึ่ง
- (ข) **หนัก**
- (ค) APG *Tabs* — "Left Arrow: moves focus to the previous tab… Optionally, activates the newly focused tab"; WCAG 2.2 SC 4.1.2 Name, Role, Value
- (ง) บรรทัด 461–466:
```js
tabs.addEventListener('keydown', function(e){
    if (e.key !== 'ArrowLeft' && e.key !== 'ArrowRight') return;
    e.preventDefault();
    (document.activeElement === tabOT ? tabNT : tabOT).focus();
    (document.activeElement === tabOT ? tabNT : tabOT).click();
});
```
- (จ) ไล่ทีละบรรทัด — เริ่มที่ `tabOT`: บรรทัด 464 เงื่อนไขเป็นจริง → `tabNT.focus()` ตอนนี้ `activeElement` กลายเป็น `tabNT` แล้ว บรรทัด 465 เงื่อนไขจึงเป็น **เท็จ** → `tabOT.click()` ผลลัพธ์: โฟกัสอยู่ที่ `tabNT` (ซึ่งถูกตั้งเป็น `aria-selected="false"`) แต่พาเนลแสดงหนังสือพันธสัญญาเดิม และ `tabOT` ถูกมาร์กว่า selected เริ่มจาก `tabNT` ก็กลับด้านแบบเดียวกัน กดซ้ำกี่ครั้งก็สลับไปมาโดยโฟกัสกับ selection อยู่คนละแท็บตลอด ไม่มีวันตรงกัน ผู้ใช้คีย์บอร์ดจึง**เลือกพันธสัญญาใหม่ด้วยลูกศรไม่ได้เลย** และสกรีนรีดเดอร์อ่านสถานะผิด
- **แก้:** เก็บค่าไว้ก่อนย้ายโฟกัส และแยกฟังก์ชันเลือกแท็บออกมาไม่ให้พึ่ง `.click()`:
```js
function selectTab(t){
  testament = (t === tabOT) ? 'OT' : 'NT';
  [tabOT, tabNT].forEach(function(x){
    var on = (x === t);
    x.setAttribute('aria-selected', String(on));
    x.tabIndex = on ? 0 : -1;              // roving tabindex, ดูข้อ ข3
  });
  showBooks(); t.focus();
}
tabs.addEventListener('keydown', function(e){
  var order = [tabOT, tabNT], i = order.indexOf(document.activeElement);
  if (i < 0) return;
  var next;
  if (e.key === 'ArrowRight') next = order[(i+1) % order.length];
  else if (e.key === 'ArrowLeft') next = order[(i-1+order.length) % order.length];
  else if (e.key === 'Home') next = order[0];
  else if (e.key === 'End') next = order[order.length-1];
  else return;
  e.preventDefault(); selectTab(next);
});
```

### ก4. `aria-labelledby` ของ `#bmGrid` ค้างชี้ไปที่แท็บพันธสัญญา ทำให้ชื่อพาเนลผิดตลอดขั้นเลือกบทและเลือกข้อ
- (ข) **หนัก**
- (ค) WCAG 2.2 SC 4.1.2 Name, Role, Value; SC 1.3.1
- (ง) บรรทัด 306 กับ 395 เทียบกับ 400–427:
```html
<div class="grid books" id="bmGrid" role="tabpanel" tabindex="-1" aria-labelledby="tabOT"></div>
```
```js
grid.setAttribute('aria-labelledby', testament === 'OT' ? 'tabOT' : 'tabNT');   // 395 — ตั้งใน showBooks
```
  `showChapters` (400–411) และ `showVerses` (412–427) ไม่เคยล้างหรือเปลี่ยนค่านี้
- (จ) หลังกด "ปฐมกาล" `grid.focus()` (บรรทัด 410) ทำให้สกรีนรีดเดอร์ประกาศชื่อพาเนล ซึ่งยังคำนวณได้ว่า **"พันธสัญญาเดิม, แผงแท็บ"** ทั้งที่เนื้อหาคือบทที่ 1–50 ของปฐมกาล (accname spec ระบุว่า element ที่ถูกอ้างโดย `aria-labelledby` ยังใช้คำนวณชื่อได้แม้ถูกซ่อน จึงไม่ช่วยแม้ ก2 จะแก้แล้ว)
- **แก้:** ในขั้นบท/ข้อ ให้ `grid.removeAttribute('aria-labelledby')`, `grid.setAttribute('role','group')` และตั้ง `grid.setAttribute('aria-label', bk[0] + ' — เลือกบท (' + bk[1] + ' บท)')` แล้วคืน `role="tabpanel"` + `aria-labelledby` เฉพาะตอนกลับมา `showBooks()`

### ก5. `#goBtn` ไม่มี event listener ใด ๆ และช่องกรอกไม่ได้อยู่ใน `<form>` → เส้นทางหลักของหน้าเว็บกดไม่ได้ทั้งเมาส์และคีย์บอร์ด
- (ข) **หนัก**
- (ค) WCAG 2.2 SC 1.3.1 Info and Relationships (semantics ของฟอร์ม/ค้นหา); SC 3.3.2 Labels or Instructions (ไม่ได้ยืนยันจาก Understanding page)
- (ง) บรรทัด 250–258 ไม่มี `<form>` ห่อ และตลอดทั้งสคริปต์บรรทัด 314–483 มีคำว่า `goBtn` ปรากฏครั้งเดียวคือใน HTML บรรทัด 253:
```html
<button type="button" class="go-btn" id="goBtn">
```
  ไม่มี `$('goBtn').addEventListener(...)` เลย
- (จ) ผลคือทั้ง Enter ในช่องกรอก **และ** การกดปุ่ม "ค้นหา" ไม่ทำอะไรเลย ผู้ทดสอบด้วยคีย์บอร์ดจึงไม่มีทางค้นพบช่องว่างของ Enter เพราะปุ่มก็ตายเหมือนกัน ข้อสังเกตที่ถูกต้อง: ปุ่มเป็น `<button>` จริง จึงกดด้วยคีย์บอร์ดได้เมื่อมีโค้ด — นี่**ไม่ใช่**การตก SC 2.1.1 Keyboard แต่การที่ Enter ในช่องค้นหาไม่ทำงานกระทบผู้ใช้สกรีนรีดเดอร์และผู้ใช้ที่ขยับมือลำบากมากเป็นพิเศษ เพราะต้องหาปุ่มเพิ่มอีกจุด
- **แก้:** ห่อด้วย `<form role="search" action="/read">` และเปลี่ยนปุ่มเป็น `type="submit"` จะได้สามอย่างฟรี: Enter ทำงานเอง, ได้ landmark `search` (ช่วยข้อ ข11), และคีย์บอร์ดบนมือถือแสดงปุ่ม "ค้นหา" แทน "ขึ้นบรรทัดใหม่" พร้อมกันนั้นเปลี่ยน `type="text"` เป็น `type="search"`

### ก6. `trap()` ผูกกับตัวไดอะล็อกเอง จึงยิงไม่ได้เมื่อโฟกัสอยู่นอกไดอะล็อก และยอมแพ้เมื่อไม่มี element ที่โฟกัสได้
- (ข) **กลาง** (เป็นต้นตอเชิงโครงสร้างของ ก1)
- (ค) APG *Dialog (Modal)* — "Tab and Shift + Tab do not move focus outside the dialog"
- (ง) บรรทัด 331–340, 359, 453:
```js
if (!items.length) return;                 // บรรทัด 336 — ปล่อยให้ Tab หลุดออกนอกไดอะล็อก
```
```js
drawer.addEventListener('keydown', function(e){ trap(drawer, e); });   // 359
modal.addEventListener('keydown', function(e){ trap(modal, e); });     // 453
```
- (จ) สองปัญหา: (1) เมื่อโฟกัสอยู่นอกกล่อง keydown ไม่ bubble ผ่านกล่อง ตัวดักจึงเงียบ — นี่คือเหตุที่ ก1 กลายเป็นเรื่องร้ายแรง (2) กรณี `items.length === 0` โค้ดเลือก `return` ซึ่งเท่ากับปล่อยโฟกัสออกนอกไดอะล็อก ตอนนี้ยังไม่เกิดเพราะปุ่มปิดมีอยู่เสมอ แต่จะเกิดทันทีที่มี empty state ในอนาคต และ `.modal-card` ไม่มี `tabindex="-1"` จึงรับโฟกัสแทนไม่ได้ด้วยซ้ำ
- **แก้:** เติม `tabindex="-1"` ที่ `.modal-card` และ `#drawer` เปลี่ยน `if (!items.length) return;` เป็น `if (!items.length){ e.preventDefault(); box.focus(); return; }` และย้าย listener ไปที่ `document` โดยเช็ก `if (!box.contains(document.activeElement)){ e.preventDefault(); (items[0]||box).focus(); }` ทางที่ดีที่สุดสำหรับหน้าจริงคือใช้ `<dialog>` + `.showModal()` ซึ่งได้ focus trap, Escape, top layer และ `inert` พื้นหลังจากเบราว์เซอร์ฟรีทั้งหมด

# ส่วน ข · ข้อค้นพบด้านการเข้าถึง (เรียงจากหนักไปเบา)

### ข1. พื้นหลังไม่ถูกทำ inert ทั้งสองไดอะล็อก — ประกาศ `aria-modal="true"` โดยที่โค้ดไม่ได้บังคับ modal จริง
- (ข) **หนัก**
- (ค) APG *Dialog (Modal)* หมายเหตุ WAI-ARIA (ยืนยันข้อความแล้ว)
- (ง) บรรทัด 279 และ 296:
```html
<aside class="drawer" id="drawer" role="dialog" aria-modal="true" aria-label="เมนู" hidden>
<div class="modal-card" role="dialog" aria-modal="true" aria-labelledby="bmTitle">
```
  ทั้งไฟล์ไม่มีคำว่า `inert` หรือ `aria-hidden` บน `<header>`/`<main>` เลย (ตรวจแล้ว: 0 ครั้ง)
- (จ) APG เขียนไว้ตรง ๆ ว่า *"mark a dialog modal only when both: Application code prevents all users from interacting in any way with content outside of it. Visual styling obscures the content outside of it."* และเตือนว่า *"users of those technologies will experience severe negative ramifications if a dialog is marked modal but does not behave as a modal for other users."* ที่นี่ข้อแรกไม่จริง: ตัวดัก Tab มีรูรั่ว (ก1/ก6) และไม่มี `inert` กันไว้อีกชั้น สำหรับ `.scrim` ยังมีประเด็นเสริม — มันคลุมแค่ `.frame` (`position:absolute;inset:0` บรรทัด 133 ภายใน `.frame{position:relative}` บรรทัด 45) ในหน้าจริงที่ไม่มีกรอบจำลอง ต้องเป็น `position:fixed` มิฉะนั้นเนื้อหานอกกรอบยังคลิกได้ ข้อสังเกตเสริม: หากโฟกัสหลุดไปยัง element ที่อยู่ใต้ scrim จะเกิดการตก **SC 2.4.11 Focus Not Obscured (Minimum)** ด้วย เพราะ scrim ทึบคลุมมันทั้งชิ้น ("the component is not entirely hidden due to author-created content" — ยืนยันข้อความแล้ว)
- **แก้:** ขณะเปิดไดอะล็อก ตั้ง `inert` บน `<header>` และ `<main>` (สองพี่น้องที่เหลือ) แล้วถอดออกตอนปิด หรือใช้ `<dialog>.showModal()` ที่ทำให้ทั้งหมดนี้ฟรี เก็บ `aria-modal="true"` ไว้ได้เมื่อ inert ทำงานจริงแล้วเท่านั้น

### ข2. ตะแกรงปุ่ม 39–150 ปุ่มไม่ประกาศจำนวน ไม่ประกาศการเปลี่ยนบริบท และปุ่มตัวเลขไม่มีชื่อที่สื่อความหมาย
- (ข) **หนัก**
- (ค) WCAG 2.2 SC 4.1.2 Name, Role, Value; SC 1.3.1 Info and Relationships; SC 2.4.6 Headings and Labels
- (ง) บรรทัด 306 (`<div class="grid books" id="bmGrid">` เป็น div เปล่า) และ 407–409:
```js
for (var c = 1; c <= bk[1]; c++){
  (function(c){ grid.appendChild(mkBtn(String(c), function(){ showVerses(bk, c); })); })(c);
}
grid.focus();
```
  `mkBtn` (384–389) ตั้งเพียง `b.textContent = label;` ไม่มี `aria-label` และตลอดไฟล์ไม่มี `aria-live` / `role="status"` เลย (ตรวจแล้ว: 0 ครั้ง)
- (จ) สิ่งที่ผู้ใช้สกรีนรีดเดอร์ได้ยินจริง: หลังกด "สดุดี" `grid.focus()` ประกาศชื่อพาเนลที่ค้างผิด (ก4) แล้วเงียบ ไม่มีคำว่า "150 บท" ไม่มีคำว่า "สดุดี" ไม่มีการบอกว่าเนื้อหาเปลี่ยนไปแล้ว จากนั้นเมื่อเดินลงมาจะได้ยิน "1 ปุ่ม, 2 ปุ่ม, 3 ปุ่ม…" ไปเรื่อย ๆ 150 ครั้ง โดยไม่มีอะไรบอกว่า 1 คืออะไร ในโหมด browse ของ NVDA/JAWS `<div>` ที่มีปุ่มลูกไม่ให้จำนวนสมาชิก เพราะมันไม่ใช่ list/grid `<h2 id="bmTitle">` อัปเดตข้อความจริง (บรรทัด 401, 413) แต่ไม่มีอะไรประกาศ และชื่อของไดอะล็อกที่ผูกด้วย `aria-labelledby="bmTitle"` จะถูกอ่านแค่ตอนเปิดเท่านั้น ไม่อ่านซ้ำเมื่อเปลี่ยน
- **แก้:** สามอย่างรวมกัน — (1) ตั้งชื่อให้ปุ่มแต่ละใบ: `b.setAttribute('aria-label','บทที่ '+c)` (ผ่าน SC 2.5.3 Label in Name เพราะชื่อที่เข้าถึงได้ยังมีสตริง "1" ที่มองเห็นอยู่) และ `'ข้อ '+v` สำหรับข้อ (2) ทำให้นับได้: ห่อปุ่มด้วย `<ul>`/`<li>` (หรือ `role="list"`/`role="listitem"`) เพื่อให้สกรีนรีดเดอร์อ่าน "รายการ 150 รายการ" (3) เพิ่มภูมิภาคประกาศสถานะ `<p id="bmStatus" class="sr" role="status"></p>` ในไดอะล็อก แล้วตั้ง `bmStatus.textContent = 'สดุดี — เลือกบท 150 บท'` ทุกครั้งที่สลับเนื้อหา คู่กับ `aria-label` ที่ถูกต้องบนคอนเทนเนอร์ตาม ก4

### ข3. Tabs pattern: ไม่มี roving tabindex, ไม่มี Home/End, และแท็บสองใบชี้ `aria-controls` ไปที่พาเนลเดียวกัน
- (ข) **กลาง**
- (ค) APG *Tabs* (ยืนยันข้อความแล้ว): "Tab: When focus moves into the tab list, places focus on the active tab element. When the tab list contains the focus, moves focus to the next element in the page tab sequence outside the tablist, which is the tabpanel"; "Each element with role tab has the property aria-controls referring to its associated tabpanel element"
- (ง) บรรทัด 302–306:
```html
<button type="button" role="tab" id="tabOT" aria-selected="true"  aria-controls="bmGrid">พันธสัญญาเดิม</button>
<button type="button" role="tab" id="tabNT" aria-selected="false" aria-controls="bmGrid">พันธสัญญาใหม่</button>
```
  ไม่มี `tabindex` บนแท็บทั้งสอง จึงได้ `tabindex=0` โดยปริยายทั้งคู่ และไม่มีการจัดการ `Home`/`End` ในบรรทัด 461–466
- (จ) ผลคือ Tab เดินผ่านแท็บทีละใบเหมือนปุ่มธรรมดา ผิดจากที่ผู้ใช้ที่คุ้นกับ pattern นี้คาด — Tab ควรกระโดดจากแท็บที่ active ไปยัง tabpanel ทันที ส่วน `aria-controls` ซ้ำกันสองใบเป็นผลจากการมี tabpanel เดียว: แท็บที่ไม่ได้เลือกจึงชี้ไปยังพาเนลที่ `aria-labelledby` ระบุว่าเป็นของอีกแท็บ Home/End เป็น optional ใน APG จึงเป็นแค่ข้อเสนอ
- **แก้:** ใช้ `selectTab()` ในข้อ ก3 ซึ่งรวม roving tabindex และ Home/End ไว้แล้ว ข้อเสนอเชิงโครงสร้างที่แรงกว่า: **หน้าต่างนี้ไม่ใช่ Tabs แต่เป็น wizard สามขั้น** — ขั้นที่ 2 และ 3 ไม่มี tab ควบคุมพาเนลอีกแล้ว (ดู ก2, ก4) พิจารณาเปลี่ยนแท็บสองใบเป็นกลุ่มปุ่มกรอง (`role="group"` + `aria-pressed`) หรือใช้ `role="radiogroup"` แล้วให้ตะแกรงเป็น `role="group"` เฉย ๆ จะซื่อสัตย์กว่าและลบปัญหา ก2/ก4 ไปในตัว

### ข4. หน้าจริงไม่มี `<h1>` — ชื่อเว็บเป็น `<p class="wordmark">` และ `<h1>` ที่มีอยู่อยู่นอกหน้าจริง
- (ข) **กลาง**
- (ค) WCAG 2.2 SC 1.3.1 Info and Relationships; SC 2.4.6 Headings and Labels; กฎ best-practice ของ axe: `page-has-heading-one`, `heading-order`
- (ง) บรรทัด 203 (นอกกรอบ) เทียบกับ 237 (ในหน้าจริง):
```html
<div class="wf-bar"><h1>โครงหน้าหลัก — พระคำ.ชีวิต รุ่น 3</h1>          <!-- ไม่ใช่หน้าจริง -->
...
<p class="wordmark">พระคำ.ชีวิต</p>                                     <!-- 2.4rem หนา จัดกลาง = หัวข้อทางสายตา -->
```
  หัวข้อเดียวในส่วนหน้าจริงคือ `<h2 id="bmTitle">` บรรทัด 298 ซึ่งอยู่ในไดอะล็อก
- (จ) เมื่อถอดแถบเครื่องมือออก หน้าจริงจะมี h2 โดยไม่มี h1 นำ — axe จะยิงทั้ง `page-has-heading-one` และ `heading-order` (ทั้งคู่อยู่ในชุด best-practice ที่โปรเจกต์พี่น้องน่าจะเปิดใน CI) และผู้ใช้สกรีนรีดเดอร์ที่เดินด้วยปุ่ม H จะไม่พบอะไรใน `<main>` เลย ข้อความ `.wordmark` สื่อความเป็นหัวข้อผ่านขนาดและน้ำหนักฟอนต์อย่างเดียว ซึ่งคือนิยามตรง ๆ ของการตก SC 1.3.1 นอกจากนี้ `<span class="brand">` บรรทัด 217 ซ้ำข้อความเดียวกับ `.wordmark` โดยไม่เป็นลิงก์กลับหน้าแรก ผู้ใช้จะได้ยินชื่อเว็บสองครั้งโดยไม่รู้ว่าต่างกันอย่างไร
- **แก้:** เปลี่ยน `<p class="wordmark">` เป็น `<h1 class="wordmark">` (CSS เดิมใช้ต่อได้ เพราะกำหนด `font-size`/`margin` เองอยู่แล้ว) และทำ `.brand` ในหัวเว็บให้เป็นลิงก์กลับหน้าแรก อาจเสริม `<h2 class="sr">ค้นหาพระคัมภีร์</h2>` เหนือกลุ่มค้นหาเพื่อให้เดินด้วยหัวข้อได้

### ข5. ความต่างสีของขอบและพื้นปุ่มต่ำมาก และเป็นการตัดสินใจที่จะติดไปถึงดีไซน์จริง
- (ข) **กลาง** (จะเป็น **หนัก** ทันทีถ้าลงสีจริงโดยรักษาอัตราส่วนเดิม)
- (ค) WCAG 2.2 SC 1.4.11 Non-text Contrast (AA, ต้องการ 3:1 สำหรับขอบเขตที่จำเป็นต่อการระบุตัวส่วนติดต่อ)
- (ง) บรรทัด 15–16 และ 189–192:
```css
--ink-soft:#6b6b6b; --line:#b5b5b5; --line-soft:#d6d6d6;
--box:#e9e9e9; --box-2:#dedede; --paper:#ffffff;
```
```css
.grid button{ min-height:44px; ... background:var(--box); border:1px solid var(--line-soft); ... }
.grid button:hover{background:var(--box-2)}
```
- (จ) คำนวณจากค่าจริงในไฟล์ (ไม่ใช่การให้คะแนนโทนเทาเอง แต่เป็นอัตราส่วนที่จะรอดไปถึงดีไซน์จริงถ้าแค่เปลี่ยนสีโดยคงระยะห่างเดิม):
  - `#d6d6d6` บน `#ffffff` = **1.45:1** — ขอบของปุ่มในตะแกรงทั้ง 150 ใบ ตก 3:1
  - `#b5b5b5` บน `#ffffff` = **2.05:1** — ขอบของ `.pill`, `.icon-x`, `.tabs button`, `.menu-btn` ตก 3:1
  - `#e9e9e9` (พื้นปุ่ม) บน `#ffffff` = **1.21:1** — เมื่อขอบก็จาง พื้นก็จาง ปุ่มแทบไม่มีขอบเขตที่มองเห็นได้เลยสำหรับผู้ใช้สายตาเลือนราง ซึ่งเป็นกลุ่มที่ระบุไว้ในบริบท (ผู้อ่านสูงอายุ)
  - `:hover` เปลี่ยนจาก `#e9e9e9` เป็น `#dedede` = ต่างกันราว 1.08:1 มองแทบไม่ออก
  - ในทางกลับกัน **`--ink-soft:#6b6b6b` บน `#ffffff` = 5.32:1 ผ่าน SC 1.4.3 ระดับ AA สบาย ๆ** ตามที่ถูกขอให้ตรวจ ไม่ต้องแก้ (แต่เหลือ headroom ไม่มาก และถูกใช้กับ `.lead` และ `.crumb` ซึ่งเป็นเนื้อหาที่ไม่ควรทำให้จางลงอีก) และ `--ink:#2f2f2f` บน `--box` = 11.7:1, `--focus:#1f1f1f` บน `#ffffff` = 16.5:1 ดีมาก
  - หมายเหตุ CI: **axe ไม่มีกฎอัตโนมัติสำหรับ SC 1.4.11** ข้อนี้จึงจะไม่ถูกจับใน pipeline ต้องตรวจด้วยคน
- **แก้:** ตอนแปลงเป็นสีจริง ตั้งเป้าให้ขอบปุ่มเทียบพื้นหลังหน้าอย่างน้อย 3:1 (เช่นขยับ `--line-soft` ให้เข้มระดับ `#767676` ขึ้นไปเมื่อวางบนขาว) และให้สถานะ hover/active ต่างกันอย่างน้อย 3:1 หรือเพิ่มสัญญาณที่ไม่ใช่สี

### ข6. ป้ายกำกับที่มองเห็นได้ของช่องค้นหามีแค่ `placeholder` ซึ่งหายไปเมื่อเริ่มพิมพ์
- (ข) **กลาง**
- (ค) WCAG 2.2 SC 3.3.2 Labels or Instructions (ไม่ได้ยืนยันจาก Understanding page); SC 2.4.6 Headings and Labels
- (ง) บรรทัด 249–251:
```html
<label class="sr" for="ref">พิมพ์ชื่อหนังสือ บท และข้อ</label>
<input id="ref" type="text" placeholder="พิมพ์ชื่อหนังสือ บท ข้อ เช่น มัทธิว 2:1-2" ...>
```
- (จ) ด้าน **โปรแกรม** ถูกต้องแล้ว — `for`/`id` ผูกกัน axe ผ่านกฎ `label` และ SC 4.1.2 ผ่าน ปัญหาอยู่ที่ด้าน **สายตา**: ผู้ใช้ที่มีข้อจำกัดด้านความจำระยะสั้นหรือความรู้ความเข้าใจ (และผู้อ่านสูงอายุตามบริบทที่ให้มา) จะเสียตัวอย่างรูปแบบ "มัทธิว 2:1-2" ทันทีที่พิมพ์ตัวแรก และค่า placeholder ของเบราว์เซอร์ส่วนใหญ่อยู่ราว 4.5:1 พอดีเส้น ซึ่งเสี่ยงตก SC 1.4.3 ถ้าไม่กำหนดสีเอง
- **แก้:** แสดงป้ายกำกับจริงเหนือกลุ่มค้นหา หรือคงข้อความตัวอย่างเป็นข้อความถาวรใต้ช่อง (ผูกด้วย `aria-describedby`) แทนที่จะฝากไว้กับ placeholder อย่างเดียว ปุ่มตัวอย่างสามใบ (บรรทัด 270–272) ช่วยได้บางส่วนอยู่แล้ว

### ข7. `.pill:focus-within` วาดกรอบโฟกัสรอบกล่องทั้งใบ ทำให้บอกไม่ได้ว่าโฟกัสอยู่ที่ตัวควบคุมใดในสาม
- (ข) **กลาง**
- (ค) WCAG 2.2 SC 2.4.7 Focus Visible; SC 2.4.13 Focus Appearance (ระดับ **AAA** ตามข้อความที่ยืนยันแล้ว จึงเป็นเป้าหมายเสริม ไม่ใช่ข้อบังคับของ AA)
- (ง) บรรทัด 94, 105, 196:
```css
.pill:focus-within{outline:3px solid var(--focus);outline-offset:2px}
.pill input:focus{outline:none}
:focus-visible{outline:3px solid var(--focus);outline-offset:2px}
```
- (จ) `.pill` มีลูกสามตัวที่โฟกัสได้ (`#pickBtn`, `#ref`, `#goBtn`) เมื่อ Tab ไปที่ปุ่ม "เลือกหนังสือ" จะได้กรอบ **สองชั้นพร้อมกัน** — กรอบเล็กรอบปุ่มจาก `:focus-visible` และกรอบใหญ่กว้าง 620px รอบกล่องทั้งใบจาก `:focus-within` กรอบใหญ่กลบสัญญาณของกรอบเล็ก และเมื่อโฟกัสอยู่ที่ช่องพิมพ์ (ซึ่งกรอบของตัวเองถูกลบด้วย `outline:none`) ตัวบ่งชี้เดียวคือกรอบรอบกล่องทั้งใบ ซึ่งกินพื้นที่ของปุ่มอีกสองใบด้วย จึงไม่ได้ระบุ "ส่วนประกอบที่รับโฟกัส" ตามเจตนาของ SC 2.4.13 ("an area of the focus indicator… at least as large as the area of a 2 CSS pixel thick perimeter of the unfocused component") อีกจุดคือ `:focus-within` ไม่ใช่ `:focus-visible` จึงติดขึ้นเมื่อคลิกด้วยเมาส์เช่นกัน
- **แก้:** ลบ `.pill input:focus{outline:none}` แล้วให้ช่องพิมพ์มีตัวบ่งชี้ของตัวเองภายในกล่อง (เช่น `outline:3px solid var(--focus); outline-offset:-3px`) และตัด `.pill:focus-within` ทิ้ง หรือถ้าอยากคงกรอบรวมไว้ ให้จำกัดเป็น `.pill:has(input:focus-visible)` เท่านั้น

### ข8. เส้นกรอบโฟกัสของปุ่มแถวแรกในตะแกรงถูกตัดด้วย `overflow:auto` เพราะ padding บนน้อยกว่าที่กรอบต้องการ
- (ข) **เบา**
- (ค) WCAG 2.2 SC 2.4.13 Focus Appearance (AAA); เกี่ยวข้องกับ SC 2.4.11 Focus Not Obscured (Minimum) แต่ **ยังไม่ตก** เพราะข้อความที่ยืนยันแล้วเขียนว่า "not *entirely* hidden"
- (ง) บรรทัด 184 กับ 196:
```css
.grid{display:grid;gap:.4rem;padding:.2rem .9rem 1rem;overflow:auto}
:focus-visible{outline:3px solid var(--focus);outline-offset:2px}
```
- (จ) กรอบโฟกัสกินพื้นที่ 2px (offset) + 3px (ความหนา) = **5px** รอบตัวปุ่ม แต่ `padding-top` ของ `.grid` = `.2rem` = **3.2px** และ `.grid` เป็น scroll container (`overflow:auto`) จึงตัดส่วนที่ล้นด้านบน ทำให้ 1.8px บนสุดของกรอบหายไปเมื่อโฟกัสอยู่แถวแรกและตะแกรงเลื่อนอยู่ที่ตำแหน่งบนสุด ด้านซ้าย/ขวา `.9rem` = 14.4px และด้านล่าง `1rem` = 16px เพียงพอ นอกจากนี้เมื่อ `grid.focus()` ถูกเรียก (บรรทัด 410, 426) หลังการ **คลิกเมาส์** เบราว์เซอร์มักไม่จับคู่ `:focus-visible` ผู้ใช้เมาส์จึงไม่เห็นเลยว่าโฟกัสย้ายไปที่พาเนลสูงเกือบพันพิกเซลแล้ว
- **แก้:** เปลี่ยน `.grid` เป็น `padding:.5rem .9rem 1rem` (8px ≥ 5px) และตรวจ container ที่มี `overflow` ทุกตัวด้วยเกณฑ์เดียวกัน

### ข9. เทคนิค `.sr` ซ่อนด้วยสายตาใช้ `clip` แบบเก่าอย่างเดียว และไม่ล้าง padding/border
- (ข) **เบา**
- (ค) เทคนิคทั่วไป ไม่ใช่การตก SC โดยตรง (`for`/`id` ทำให้ SC 1.3.1 และ 4.1.2 ผ่านอยู่แล้ว)
- (ง) บรรทัด 197:
```css
.sr{position:absolute;width:1px;height:1px;overflow:hidden;clip:rect(0 0 0 0);white-space:nowrap}
```
- (จ) ใช้งานได้จริงในสภาพปัจจุบัน — `clip` ต้องการ `position:absolute` ซึ่งมีครบ และ containing block คือ `.frame{position:relative}` (บรรทัด 45) จึงไม่ทำให้หน้าเลื่อน แต่ `clip` ถูกประกาศเลิกใช้แล้วและไม่มี `clip-path` สำรอง อีกทั้งไม่ได้ล้าง `padding`/`border`/`margin` ซึ่งจะทำให้กล่อง 1px โผล่ทันทีที่มี reset ของโปรเจกต์จริงใส่ padding ให้ element ทั่วไป
- **แก้:**
```css
.sr{position:absolute;width:1px;height:1px;padding:0;margin:-1px;overflow:hidden;
    clip:rect(0 0 0 0);clip-path:inset(50%);white-space:nowrap;border:0}
```

### ข10. โฟกัสอัตโนมัติที่ช่องพิมพ์ตอนโหลดหน้า ทำให้ผู้ใช้สกรีนรีดเดอร์ข้ามหัวเว็บและชื่อเว็บไปเลย
- (ข) **เบา**
- (ค) ไม่ตก SC ข้อใดโดยตรง (ไม่มี change of context จึงไม่ใช่ SC 3.2.1) แต่ขัดกับกลุ่มผู้ใช้ที่ระบุไว้
- (ง) บรรทัด 480–482:
```js
// จอคอมพิวเตอร์: ให้เคอร์เซอร์รออยู่ในช่องพิมพ์ตั้งแต่เปิดหน้า จะได้พิมพ์ได้เลยไม่ต้องคลิกก่อน
if (!frame.classList.contains('mobile')) $('ref').focus({ preventScroll: true });
```

- (จ) เหตุผลที่เขียนกำกับไว้สมเหตุสมผลและการยกเว้นบนมือถือถูกต้องมาก (คีย์บอร์ดจะไม่เด้ง) แต่ผลข้างเคียงคือผู้ใช้สกรีนรีดเดอร์ถูกวางลงกลางฟอร์มโดยไม่ได้ยินชื่อเว็บ ประโยคนำ หรือรู้ว่ามีเมนูอะไรบ้าง และผู้ใช้แว่นขยายจะเห็นวิวพอร์ตกระโดด (แม้ `preventScroll` จะช่วยลดไปมากแล้ว) หน้าแรกที่มีเนื้อหาน้อยแบบนี้ถือว่าความเสี่ยงต่ำกว่าปกติ จึงให้ **เบา** ไม่ใช่ **กลาง**

### ข11. ความสัมพันธ์เชิงโครงสร้างที่ขาด: ไม่มี landmark `search`, กลุ่มปุ่มตัวอย่างไม่ผูกกับคำอธิบาย, เบรดครัมบ์ไม่เป็น nav, อักขระ ‹ › ถูกอ่านออกเสียง
- (ข) **เบา**
- (ค) WCAG 2.2 SC 1.3.1 Info and Relationships
- (ง) บรรทัด 268–273 และ 404–419:
```html
<div class="examples">
  <span class="cap">ลองกดตัวอย่าง</span>
  <button type="button" class="ex">ยอห์น 3:16</button>
```
```js
crumb.appendChild(mkBtn('‹ หนังสือ', showBooks));
crumb.appendChild(document.createTextNode(' › ' + bk[0]));
```
- (จ) สี่จุดเล็ก ๆ: (1) `<span class="cap">` เป็นป้ายกำกับทางสายตาของกลุ่มปุ่มตัวอย่าง แต่ไม่มีการผูกเชิงโปรแกรม (2) กลุ่มค้นหาทั้งก้อนไม่มี landmark `search` ทำให้ข้ามไปหาไม่ได้ (แก้พร้อมกับ ก5 ได้เลย) (3) `#bmCrumb` เป็น `<div>` เปล่า ควรเป็น `<nav aria-label="เส้นทาง">` (4) `‹` และ `›` เป็นข้อความจริงในชื่อของปุ่ม สกรีนรีดเดอร์บางตัวจะอ่านว่า "single left-pointing angle quotation mark" คั่นกลาง ตรงนี้ตรงข้ามกับปุ่ม `×` ที่ทีมทำถูกแล้วด้วย `aria-label` (บรรทัด 282, 299)
- **แก้:** `<div class="examples" role="group" aria-labelledby="exCap">` + `<span class="cap" id="exCap">`; `<form role="search">` ตาม ก5; เปลี่ยน `#bmCrumb` เป็น `<nav aria-label="เส้นทาง">`; ห่อลูกศรด้วย `<span aria-hidden="true">‹</span>` แล้วให้ปุ่มมี `aria-label="กลับไปเลือกหนังสือ"`

### ข12. `body{font-size:16px}` เป็นค่าสัมบูรณ์ ลบล้างขนาดตัวอักษรเริ่มต้นที่ผู้ใช้ตั้งไว้ในเบราว์เซอร์
- (ข) **เบา**
- (ค) ไม่ตก SC 1.4.4 Resize Text (การซูมยังทำงานครบ) แต่ขัดกับกลุ่มผู้อ่านสูงอายุตามบริบทที่ให้มา
- (ง) บรรทัด 24:
```css
font-size:16px; line-height:1.6;
```
- (จ) ทุกอย่างที่เหลือในไฟล์ใช้ `rem`/`em` อย่างสม่ำเสมอ ซึ่งดีมาก แต่รากถูกตรึงที่ 16px ผู้ใช้ที่เข้าไปตั้ง "ขนาดตัวอักษร: ใหญ่" ในการตั้งค่าเบราว์เซอร์ (ซึ่งเป็นวิธีที่ผู้สูงอายุใช้บ่อยกว่าการซูม) จะไม่ได้อะไรเลยจากหน้านี้ ข้อสังเกตเสริม: ตัวอักษรเล็กสุดในส่วนหน้าจริงคือ `.85rem` = 13.6px (`.examples .cap`) และ `.9rem` = 14.4px (ปุ่มในตะแกรง, เบรดครัมบ์) — WCAG ไม่กำหนดขนาดขั้นต่ำ แต่อักษรไทยมีสระบนล่างและวรรณยุกต์ ที่ 14.4px จะแยกแยะยากกว่าอักษรละตินขนาดเดียวกันอย่างมีนัยสำคัญ
- **แก้:** ใช้ `font-size:100%` บน `html` แล้วปรับ scale ด้วย `rem` และพิจารณายกพื้นตัวอักษรที่เล็กที่สุดในหน้าจริงขึ้นเป็น `.95rem`

# ผ่านแล้ว — สิ่งที่ไฟล์นี้ทำถูกต้องแล้ว อย่าให้หายตอนเขียนใหม่

1. **ขนาดเป้าสัมผัสผ่าน SC 2.5.8 (24×24) ทุกจุด และผ่านเกณฑ์แนะนำ 44px ด้วย** คำนวณจาก CSS จริง: `.grid.nums` บนจอคอม = (560 − 2×14.4 − 7×6.4)/8 = **60.8 × ≥44px**; บนมือถือ = (304 − 28.8 − 4×6.4)/5 = **49.9 × ≥44px**; `.grid.books` = **128px** (คอม) และ **134.4px** (มือถือ); `.icon-x` ตั้ง `min-width:44px;min-height:44px` ชัดเจนทั้งปุ่มปิดลิ้นชักและปุ่มปิดหน้าต่าง; `.pick-btn`/`.go-btn`/`input` = 52px; `.drawer nav a` = 48px ไม่มีจุดใดต่ำกว่า 24px เลย ระยะห่างระหว่างปุ่ม 6.4px ไม่เป็นปัญหาเพราะทุกเป้าใหญ่เกิน 24px อยู่แล้วจึงไม่ต้องพึ่งข้อยกเว้น Spacing
2. **Escape ทำงานได้ทุกกรณี ไม่ว่าโฟกัสจะอยู่ในหรือนอกไดอะล็อก** — บรรทัด 468–472 ผูก listener ไว้ที่ `document` ไม่ใช่ที่กล่อง และเรียงลำดับ modal ก่อน drawer ถูกต้อง นี่คือส่วนที่ทำถูกกว่าตัวดัก Tab (ก6) และไม่ควรถูกเปลี่ยนเป็น listener บนกล่อง
3. **คืนโฟกัสให้ตัวเปิดเมื่อปิดไดอะล็อก** ทั้งสองตัว — บรรทัด 345/354 (`drawerBack`) และ 435/447 (`modalBack`) พร้อมป้องกัน `if (… && …focus)` ตรงตาม APG "When a dialog closes, focus returns to the element that invoked the dialog"
4. **จุดโฟกัสแรกของหน้าต่างเลือกหนังสือเลือกมาถูก** — บรรทัด 441 `tabOT.focus()` พร้อมคอมเมนต์อธิบายเหตุผล APG อนุญาตชัดเจน: "the most appropriate focus placement will depend on the nature and size of the content" และเตือนไม่ให้วางโฟกัสไว้ที่ปุ่มที่ทำลายงานได้ การไม่โฟกัสปุ่ม `×` จึงถูกต้อง ไม่ใช่ข้อผิดพลาด
5. **ปุ่มไอคอนล้วนมีชื่อที่เข้าถึงได้** — `aria-label="ปิดเมนู"` (282) และ `aria-label="ปิดหน้าต่างเลือกหนังสือ"` (299) ทับกลิฟ `×` เรียบร้อย และ **`<svg>` ทุกตัวมี `aria-hidden="true"`** (228, 243, 254, 262) โดยมีข้อความไทยกำกับข้าง ๆ ทุกปุ่ม
6. **การซูมไม่ถูกบล็อก** — บรรทัด 5 `content="width=device-width, initial-scale=1"` ไม่มี `maximum-scale` และไม่มี `user-scalable=no` ผ่าน SC 1.4.4 และหน่วยที่เหลือทั้งหมดเป็น `rem`/`em`/`%`/`fr` อย่างสม่ำเสมอ
7. **`aria-haspopup="dialog"` + `aria-expanded` บนปุ่มเปิดครบทั้งสามใบ** (227, 242, 261) และมีการอัปเดตค่าจริงทั้งตอนเปิดและตอนปิด (347, 353, 440, 446)
8. **`[hidden]` มี CSS override รองรับถูกต้องสามในสี่จุด** — `.scrim[hidden]` (134), `.drawer[hidden]` (140), `.modal[hidden]` (155) ทีมเข้าใจปัญหานี้อยู่แล้ว ขาดแค่ `.tabs` (ก2)
9. **ตัวกรองความมองเห็นในตัวดักโฟกัสเขียนถูก** — บรรทัด 333–335 ใช้ `el.offsetWidth || el.offsetHeight || el.getClientRects().length` จึงตัด `.pick-btn` ที่เป็น `display:none` บนมือถือออกจากลูป Tab ได้จริง (ยังไม่ครอบคลุม `visibility:hidden` แต่ไฟล์นี้ไม่ได้ใช้)
10. **ไม่มีสิ่งที่ axe จะยิงในหมวดโครงสร้าง ARIA** ตรวจแล้ว: ไม่มี id ซ้ำเลย; `aria-controls` ทุกตัวชี้ไปยัง id ที่มีอยู่จริง (`drawer`, `bookModal`×2, `bmGrid`×2); `aria-labelledby` ทุกตัวชี้ไปยัง id ที่มีจริง (`bmTitle`, `tabOT`/`tabNT`); ไม่มี interactive ซ้อน interactive; `role="tab"` อยู่ใน `role="tablist"` ครบตาม `aria-required-parent`/`aria-required-children`; `<nav>` สองตัวมี `aria-label` ต่างกัน (219, 284) จึงผ่าน `landmark-unique`; ทั้ง `#drawer` และ `.modal-card` มีชื่อครบตาม `aria-dialog-name`; `#ref` มี `<label for>` ผูกถูก; `.grid` ที่ `overflow:auto` มีปุ่มโฟกัสได้อยู่ข้างในจึงผ่าน `scrollable-region-focusable`
11. **`lang="th"` ถูกต้อง** (บรรทัด 2) ซึ่งจำเป็นมากเพื่อให้สกรีนรีดเดอร์เลือกเสียงไทยและออกเสียงชื่อหนังสือได้ถูก
12. **`aria-modal="true"` ประกาศครบทั้งสองไดอะล็อก และมี scrim ทึบคู่กัน** โครงถูกแล้ว เหลือแค่เติม `inert` ให้พฤติกรรมจริงตรงกับที่ประกาศ (ข1)
13. **`autocomplete="off"` ใช้ถูกบริบท** — SC 1.3.5 Identify Input Purpose บังคับเฉพาะช่องที่เก็บข้อมูลเกี่ยวกับตัวผู้ใช้ ช่องอ้างอิงพระคัมภีร์ไม่เข้าข่าย และ `spellcheck="false"`/`autocorrect="off"` เป็นการตัดสินใจที่ถูกสำหรับชื่อเฉพาะภาษาไทย
14. **SC 2.4.11 Focus Not Obscured (Minimum) ผ่านในสภาพปกติ** — `.modal-head` เป็น flex sibling ไม่ใช่ sticky จึงไม่ทับ `.grid` และไม่มี overlay ค้างหน้าจออื่น (ความเสี่ยงเดียวคือกรณีโฟกัสหลุดใต้ scrim ซึ่งเป็นผลพวงของ ก1/ข1 ไม่ใช่ปัญหาของเลย์เอาต์เอง)
15. **ทีมคิดเรื่องการหายไปของ element ที่กำลังโฟกัสไว้แล้ว 2 ใน 3 จุด** — `showChapters` (410) และ `showVerses` (426) เรียก `grid.focus()` หลังจากล้าง DOM ที่มีปุ่มโฟกัสอยู่ ขาดแค่ `showBooks` (ก1) แปลว่าเป็นเรื่องเติมให้ครบ ไม่ใช่ต้องคิดใหม่
