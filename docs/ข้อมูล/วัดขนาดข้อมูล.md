# วัดขนาดข้อมูลก่อนยกเข้า Supabase

ใบงาน [#41](https://aimgit.aimagin.com/v3/phrakham/-/issues/41) · วัด 31 ส.ค. 2569

**ก้าวนี้วัดอย่างเดียว** ไม่ได้ยกข้อมูล ไม่ได้แตะ Supabase และไม่ได้แก้ไฟล์ใดในกองของรุ่น 2
ของที่เปิดดูคือฐานข้อมูลที่ ETL ของรุ่น 2 สร้างไว้ กับโฟลเดอร์ไฟล์ที่เว็บรุ่น 2 ดึงไปใช้

**ทุกตัวเลขในเอกสารนี้ออกมาจากคำสั่งเดียว** คือ `py -3.14 tools/วัดขนาดข้อมูล.py`
รันแล้วเอาผลมาทาบกับเอกสารได้ทีละบรรทัด รายละเอียดอยู่หัวข้อ *คำสั่งที่ใช้*

**หน่วยเดียวทั้งเอกสาร** คำว่า MB ในที่นี้หมายถึง 1,048,576 ไบต์เสมอ

## คำตอบสั้น ๆ

**แผนฟรีของ Supabase พอ** ที่เก็บฐานข้อมูลของแผนฟรีคือ 500 เมกะไบต์
ของที่รุ่น 3 ต้องยกขึ้นไปประมาณ 134.5 เมกะไบต์ เหลือที่ว่างประมาณ 365 เมกะไบต์

**แต่มีเรื่องที่ต้องระวังมากกว่าเรื่องที่เก็บ** อยู่ 2 เรื่อง เขียนไว้ท้ายหัวข้อ 4

---

## 1 ในฐานข้อมูลมีตารางอะไรบ้าง

ไฟล์ `data/phrakham.sqlite` ของรุ่น 2 มีขนาด **122,355,712 ไบต์** (116.7 MB)
บีบไฟล์แล้วเหลือ **120,193,024 ไบต์** (114.6 MB) แปลว่ามีที่ว่างค้างอยู่ราว 2 MB

มี **6 ตาราง** เรียงจากหนักไปเบา

| ตาราง | แถว | กินที่ในไฟล์ | เนื้อล้วน ๆ |
|---|---:|---:|---:|
| `word` | 613,924 | 70,713,344 ไบต์ (67.4 MB) | 42.8 MB |
| `translation_verse` | 155,372 | 43,880,448 ไบต์ (41.8 MB) | 35.0 MB |
| `lexicon_entry` | 11,520 | 3,375,104 ไบต์ (3.2 MB) | 2.7 MB |
| `verse` | 31,107 | 1,339,392 ไบต์ (1.3 MB) | 0.5 MB |
| `lexeme` | 14,769 | 872,448 ไบต์ (0.8 MB) | 0.5 MB |
| `lexeme_thai` | 4 | 8,192 ไบต์ (0.0 MB) | 3,172 ไบต์ |

**ช่อง *กินที่ในไฟล์* รวมดัชนีของตารางนั้นไว้แล้ว** จึงมากกว่าช่อง *เนื้อล้วน ๆ*

**วิธีวัด** — SQLite รุ่นที่ติดมากับ Python เครื่องนี้ไม่มีตาราง `dbstat` ที่ใช้ถามขนาดรายตารางได้
จึงวัดด้วยการถ่ายสำเนาไปที่พักชั่วคราว แล้วลบตารางทีละตัวและบีบไฟล์ ดูว่าไฟล์เล็กลงเท่าไร

## 2 แต่ละตารางเก็บอะไร

### `word` — คำภาษาเดิมทีละคำ

หนึ่งแถวคือหนึ่งคำในตัวบทฮีบรูหรือกรีก บอกรูปที่ปรากฏ คำต้นแบบ รหัสประจำคำ รหัสรูปผัน และคำแปลสั้น

```
('000001', 'Matt.1.1', 'Βίβλος', 'βίβλος', 'G976', 'N-NSF', 'c1', 'book')
('000002', 'Matt.1.1', 'γενέσεως', 'γένεσις', 'G1078', 'N-GSF', 'c1', 'origin')
('o010010010011', 'Gen.1.1', 'בְּ', 'בְּ', 'H0871a', 'R', '', '')
```

แยกตามภาษาได้ ฮีบรู 468,362 คำ อาราเมค 7,549 คำ กรีก 138,013 คำ
ฝั่งฮีบรูกับอาราเมคมีช่อง `lang` เขียนว่า `H` กับ `A` **ส่วนฝั่งกรีกปล่อยช่องนี้ว่างไว้** ไม่ได้เขียนว่า `G`

### `translation_verse` — ตัวบทแปลทีละข้อ

หนึ่งแถวคือหนึ่งข้อของหนึ่งฉบับแปล มี **5 ฉบับ**

```
('Matt.1.1', 'TCV', 'บันทึกลำดับตระกูลของพระเยซูพระเมสสิยาห์ ผู้เป็นเชื้อสายของดาวิด…')
```

| ฉบับ | ข้อ | ขนาดเนื้อ |
|---|---:|---:|
| TCV | 31,094 | 11.4 MB |
| THKJV | 31,102 | 10.9 MB |
| KJV | 31,102 | 4.3 MB |
| LSV | 30,971 | 4.3 MB |
| WEB | 31,103 | 4.1 MB |

ฉบับไทยกินที่มากกว่าฉบับอังกฤษเกือบ 3 เท่า เพราะตัวอักษรไทยหนึ่งตัวใช้ 3 ไบต์ ส่วนอังกฤษใช้ 1 ไบต์

### `lexicon_entry` — คำอธิบายศัพท์

หนึ่งแถวคือคำอธิบายของศัพท์หนึ่งคำจากพจนานุกรมหนึ่งเล่ม มี 2 เล่ม คือ abbott-smith 5,896 แถว และ strongs 5,624 แถว

```
('G2', 'abbott-smith', 'Ἀαρών', 'Aaron', '5 Ἀαρών (Heb. אַהֲרוֹן ), indecl. … Aaron ( Ex 4:14 , al.)…')
```

### `verse` — บัญชีเลขข้อ

หนึ่งแถวคือหนึ่งข้อ บอกแค่ว่าอยู่เล่มไหน บทไหน ข้อไหน และเป็นต้นย่อหน้าหรือไม่

```
('Exod.7.4', 'Exod', 7, 4, 0)
('Jer.49.22', 'Jer', 49, 22, 1)
```

### `lexeme` — บัญชีคำต้นแบบ

หนึ่งแถวคือคำต้นแบบหนึ่งคำ บอกรหัส Strong คำแปลสั้น และจำนวนครั้งที่พบ

```
('G2424', 'Ἰησοῦς', 'G2424', 'Jesus/Joshua', 917)
```

### `lexeme_thai` — บทความศัพท์ที่คนเขียนเอง

มีแค่ 4 แถว เป็นบทความภาษาไทยที่ผู้เขียนของรุ่น 2 เขียนเองประกอบศัพท์ 4 คำ
ในตัวเนื้อมีคอมเมนต์เขียนกำกับไว้เองว่ายกมาจากพจนานุกรมเพื่อการศึกษา ไม่ใช่ข้อความที่เผยแพร่

## 3 รุ่น 3 ใช้ตารางไหน

รุ่น 3 เผยแพร่ **11 แหล่ง** ชื่ออยู่ที่หัวข้อ `h3` ของ `content/แหล่งข้อมูล.md`
เอาตารางของรุ่น 2 มาทาบกับ 11 แหล่งนั้น ได้ผลแบบนี้

| ตาราง | รุ่น 3 เอาไหม | เพราะอะไร |
|---|---|---|
| `word` | **แหล่งถูกแค่ครึ่งเดียว** | ฝั่งฮีบรูแหล่งถูกแล้ว ฝั่งกรีกแหล่งผิด ดูหัวข้อย่อยข้างล่าง |
| `translation_verse` | **เอา 4 ฉบับจาก 5** | TCV, Thai KJV, WEB, LSV อยู่ใน 11 แหล่ง ส่วน **KJV อังกฤษไม่อยู่** |
| `lexicon_entry` | เอา แต่ยังไม่ครบ | Abbott-Smith กับ Strong อยู่ใน 11 แหล่ง แต่ **ขาด UBS Dictionary กับ HebrewLexicon** |
| `verse` | เอา | เป็นโครงเลขข้อ ใช้เป็นกุญแจของทุกชั้น |
| `lexeme` | เอา | เป็นบัญชีคำต้นแบบ ใช้เป็นกุญแจต่อไปหาคำอธิบาย |
| `lexeme_thai` | **ไม่เอา** | เป็นบทความของรุ่น 2 ซึ่ง [WPA.08](../wpa-08-mission-statement.md) หัวข้อ Out ข้อ 5 สั่งว่าไม่ยกมา |

### ตาราง `word` สองฝั่งมาคนละแหล่ง ต้องแยกกันตอบ

ตาราง `word` กินที่ 67.4 MB มากกว่าครึ่งของทั้งไฟล์ และ **สร้างจากคนละแหล่งกันสองฝั่ง**

| ฝั่ง | แถว | มาจาก | รุ่น 3 ใช้แหล่งนี้ไหม |
|---|---:|---|---|
| ฮีบรูกับอาราเมค | 475,911 (77.5%) | **MACULA Hebrew** | **ใช้ เป็นตัวหลักอยู่แล้ว** |
| กรีก | 138,013 (22.5%) | **OpenGNT** | **ไม่ใช้** เป็นแหล่ง #06 |

**ฝั่งฮีบรูแหล่งถูกแล้ว** `etl/build_ot.py` ของรุ่น 2 บรรทัด 2 เขียนเองว่าสร้างจาก MACULA Hebrew
และบรรทัด 23-24 ชี้ไปที่ไฟล์เดียวคือ `macula-hebrew.tsv` **ไม่ได้แตะ morphhb เลย**
เปิดหัวไฟล์ TSV นั้นดู คอลัมน์แรกชื่อ `xml:id` ค่าแรกคือ `o010010010011` ตรงกับเลขประจำคำในฐานข้อมูลพอดี

ยืนยันซ้ำอีกทางด้วยรหัสรูปผัน morphhb เขียนรหัสโดยมีตัว `H` นำหน้า เช่น `HNcfsa` ส่วน MACULA ไม่มีตัวนำ
นับแถวฝั่งฮีบรูที่รหัสขึ้นต้นด้วย `H` ได้ **0 แถว** และแถวฝั่งฮีบรูที่เลขประจำคำขึ้นต้นด้วย `o` ได้ **ครบทั้ง 475,911 แถว**

ที่ morphhb โผล่ในกองของรุ่น 2 มีที่เดียวคือ `etl/hebrew_morph.py` ซึ่งหยิบ **ไฟล์อธิบายความหมายของรหัส** มาแปลรหัสเป็นคำอ่าน
**ไม่ได้เอาตัวข้อมูลมา** และหัวไฟล์นั้นเขียนเองว่ารหัสที่ MACULA เก็บไม่มีตัวนำหน้าบอกภาษา

**ฝั่งกรีกแหล่งผิด** `etl/build_nt.py` บรรทัด 2 เขียนเองว่าสร้างจาก OpenGNT และชี้ไปที่ `OpenGNT_BASE_TEXT.zip`
OpenGNT คือแหล่ง **#06** ที่ [บันทึกแหล่งข้อมูล](../บันทึก-แหล่งข้อมูล.md) หัวข้อ ① ระบุว่า **ไม่ใช้**
รุ่น 3 ใช้ MACULA Greek แทน

⇒ **ที่ต้องสร้างใหม่เพราะแหล่งผิดจริง ๆ มีแต่ฝั่งกรีก 138,013 แถว** อีก 77.5% ของตารางมาจากแหล่งที่รุ่น 3 ใช้อยู่แล้ว

**ถึงอย่างนั้นก็ไม่ได้ยกแถวของรุ่น 2 ขึ้นไปอยู่ดี** เพราะท่อแปลงข้อมูลของรุ่น 3 สร้างชั้นคำนี้ได้เองทั้งสองฝั่ง
ได้ออกมา 613,652 คำ (เจ้าของตัวเลขคือ [ข้อมูลที่เว็บอ่าน](../ข้อมูลที่เว็บอ่าน.md))
ห่างจากของรุ่น 2 ที่ 613,924 คำ อยู่ 272 คำ **ขนาดจึงใกล้กันมากพอที่จะเอามาประมาณกันได้**

### ของที่รุ่น 3 ต้องมี แต่ไม่มีในฐานข้อมูลของรุ่น 2

- **UBS Dictionary** — ไม่มีแถวใดใน `lexicon_entry`
- **HebrewLexicon** — ไม่มีแถวใดใน `lexicon_entry` ฝั่งฮีบรูจึงยังไม่มีคำอธิบายศัพท์เลย
- **ป้ายการเน้น 33 ชนิดของ Levinsohn** — ไม่มีช่องใดในตาราง `word` รองรับ

**แปลว่าเลข 134.5 เมกะไบต์ที่จะบอกในหัวข้อถัดไป เป็นเลขขั้นต่ำ** ของจริงจะมากกว่านี้

## 4 ต้องยกขึ้น Supabase กี่เมกะไบต์ แผนฟรีพอไหม

### แผนฟรีของ Supabase ให้อะไรบ้าง

เปิดอ่านจากเว็บของ Supabase เอง 31 ส.ค. 2569 สองหน้าตรงกัน คือ
[หน้าราคา](https://supabase.com/pricing) และ [หน้าคู่มือเรื่องการคิดเงิน](https://supabase.com/docs/guides/platform/billing-on-supabase)

| อย่าง | แผนฟรีให้ |
|---|---|
| ที่เก็บฐานข้อมูล | **500 เมกะไบต์ ต่อโครงการ** |
| ที่เก็บไฟล์ | 1 กิกะไบต์ |
| ข้อมูลที่ส่งออกได้ต่อเดือน | 5 กิกะไบต์ |
| ผู้ใช้ต่อเดือน | 50,000 คน |
| โครงการที่เปิดพร้อมกันได้ | 2 โครงการ |
| **ข้อบังคับที่ต้องรู้** | **ไม่มีใครใช้ครบ 1 สัปดาห์ โครงการจะถูกหยุด** |

### ทำไมต้องคิดขนาดใหม่ ไม่ใช้เลขจากหัวข้อ 1

Supabase ไม่ได้ใช้ SQLite แต่ใช้โปรแกรมฐานข้อมูลอีกตัวชื่อ Postgres ซึ่งเก็บของกินที่ไม่เท่ากัน
Postgres มี **ของแถมติดมากับทุกแถว** อยู่ 3 อย่าง

1. ทุกแถวมีป้ายกำกับของมันเอง กินแถวละ **28 ไบต์**
2. ทุกช่องที่เก็บตัวหนังสือ มีป้ายบอกความยาวติดมาอีก **1 ถึง 4 ไบต์**
3. ทุกช่องที่เก็บตัวเลขจำนวนเต็ม กิน **4 ไบต์เสมอ** ไม่ว่าตัวเลขนั้นจะเป็น 1 หรือ 150

ของแถมพวกนี้ฟังดูนิดเดียว แต่ตาราง `word` มี 613,924 แถว คูณกันแล้วกลายเป็นหลายสิบเมกะไบต์
สคริปต์จึงเอาเลขพวกนี้ไปคูณกับจำนวนแถวจริงของแต่ละตาราง แล้วบวกที่ของดัชนีที่ใช้ค้นหาเข้าไปด้วย

### ของที่เราต้องยกขึ้นไป

| ตาราง | แถว | กองข้อมูล | ดัชนี | รวม |
|---|---:|---:|---:|---:|
| `word` | 613,924 | 71.9 MB | 17.2 MB | 89.1 MB |
| `translation_verse` | 155,372 | 39.9 MB | 4.7 MB | 44.5 MB |
| `lexicon_entry` | 11,520 | 3.1 MB | 0.2 MB | 3.4 MB |
| `verse` | 31,107 | 1.6 MB | 0.8 MB | 2.4 MB |
| `lexeme` | 14,769 | 1.0 MB | 0.3 MB | 1.3 MB |
| `lexeme_thai` | 4 | 0.0 MB | 0.0 MB | 0.0 MB |
| **รวมทุกตาราง** | | | | **140.7 MB** |

ตัดของที่รุ่น 3 ไม่เอาออก คือ KJV อังกฤษ 31,102 แถว เท่ากับ 6.2 MB กับ `lexeme_thai` อีก 4 แถว

### ⇒ เหลือ 134.5 เมกะไบต์ จากโควตา 500 เมกะไบต์ เหลือที่ว่าง 365.5 เมกะไบต์

**พอ และเหลือเยอะ** ถึงเลขจริงจะบานเป็น 2 เท่าของที่ประมาณไว้ ก็ยังไม่ถึงครึ่งของโควตา

### เรื่องที่ต้องระวังมากกว่าเรื่องที่เก็บ

**หนึ่ง — โครงการฟรีถูกหยุดถ้าไม่มีใครใช้ครบ 1 สัปดาห์**
ระหว่างที่ยังไม่เปิดเว็บให้คนนอกเข้า เว็บจะเงียบเป็นสัปดาห์ได้ง่ายมาก แล้ววันที่จะใช้จริงจะเปิดไม่ติด
เรื่องนี้เจ็บกว่าเรื่องที่เก็บเต็ม เพราะที่เก็บเต็มเรารู้ล่วงหน้า แต่การถูกหยุดมาแบบไม่ทันตั้งตัว

**สอง — ข้อมูลที่ส่งออกได้ 5 กิกะไบต์ต่อเดือน**
เนื้อที่ผู้อ่านต้องโหลดถ้าเปิดครบทุกบทคือ 55,650,328 ไบต์ (53.1 MB)
แบ่งเป็นชั้นคำภาษาเดิม 24,961,664 ไบต์ (23.8 MB) และตัวบทแปล 4 ฉบับ 30,688,664 ไบต์ (29.3 MB)
หารด้วย 1,189 บท ได้ **เฉลี่ยบทละประมาณ 46 กิโลไบต์**

⇒ โควตา 5 กิกะไบต์ เปิดบทได้เดือนละประมาณ **114,700 ครั้ง** ก่อนเต็ม

ตัวเลขนี้เป็นเนื้อดิบ ยังไม่ได้บวกโครง JSON และยังไม่ได้หักการบีบข้อมูลตอนส่ง
ทั้งสองอย่างดันคนละทาง จึงยังบอกไม่ได้ว่าสุทธิแล้วมากขึ้นหรือน้อยลง

### ถ้าวันหนึ่งไม่พอ ตัดอะไรได้บ้าง

เรียงจากตัดง่ายไปตัดยาก

1. **ไม่เก็บช่องที่ซ้ำกับกุญแจ** ตาราง `word` เก็บ `book` `chapter` `verse` ไว้ทั้งที่มี `verse_ref` อยู่แล้ว
   เนื้อสามช่องนี้รวมกัน 4,228,203 ไบต์ (4.0 MB) และใน Postgres จะมากกว่านี้เพราะช่องตัวเลขกิน 4 ไบต์เสมอ
2. **ไม่เก็บช่อง `gloss` ซ้ำในตาราง `word`** คำแปลสั้นอยู่ในตาราง `lexeme` อยู่แล้ว เนื้อช่องนี้ 4,057,609 ไบต์ (3.9 MB)
3. **ย้ายตัวบทแปลออกไปเป็นไฟล์ธรรมดา** ตัวบทแปลไม่ต้องค้นทีละคำ เก็บเป็นไฟล์ต่อบทได้ ประหยัดได้ประมาณ 38.4 MB
4. **แยกฝั่งฮีบรูกับฝั่งกรีกเป็นคนละโครงการ** แผนฟรีให้เปิดได้ 2 โครงการพอดี

**⛔ ยังไม่ต้องทำข้อใดเลยตอนนี้** ที่ว่างเหลือ 365 เมกะไบต์ ตัดตอนนี้คือแลกความง่ายทิ้งไปโดยไม่ได้อะไรกลับมา

## คำสั่งที่ใช้

ทุกตัวเลขในเอกสารนี้ออกมาจากคำสั่งเดียว รันบนวินโดวส์ด้วย Python 3.14

```
py -3.14 tools/วัดขนาดข้อมูล.py
```

กองของรุ่น 2 อยู่ที่อื่น ให้บอกที่อยู่ด้วย `py -3.14 tools/วัดขนาดข้อมูล.py --กอง <โฟลเดอร์>`

สคริปต์พิมพ์ออกมา 8 หัวข้อ เรียงตรงกับเอกสารนี้ คือ ① ขนาดไฟล์กับขนาดรายตาราง
② ตัวบทแปลแยกตามฉบับ ③ ชั้นคำภาษาเดิมมาจากแหล่งไหน ④ พจนานุกรมแยกตามเล่ม
⑤ **ขนาดถ้าย้ายไป Postgres กับที่ว่างที่เหลือ** ⑥ โควตาส่งออก ⑦ ช่องที่ตัดได้ ⑧ โฟลเดอร์ของเว็บรุ่น 2

**สคริปต์เปิดฐานข้อมูลแบบอ่านอย่างเดียว** ด้วย `mode=ro` จึงเขียนทับกองของรุ่น 2 ไม่ได้แม้จะพลาด
ตอนวัดขนาดรายตารางมันต้องลบตารางทิ้งจริง จึงถ่ายสำเนาไปที่พักชั่วคราวก่อน แล้วลบสำเนาทิ้งเมื่อวัดเสร็จ

### ⛔ ท่อตรวจของอัมกิตไม่ได้รันคำสั่งนี้ให้

`tools/ด่านคำสั่งเอกสาร.py` หัวไฟล์เขียนไว้เองว่ามันรันเฉพาะบล็อกที่ติดป้าย `sh`
บล็อกข้างบนไม่ได้ติดป้าย **เพราะมันต้องมีกองของรุ่น 2 ในเครื่อง ซึ่งตัวรันของอัมกิตไม่มี**

⇒ **เครื่องหมายเขียวของท่อตรวจ ไม่ใช่หลักฐานว่าคำสั่งนี้รันออก** ใครจะเชื่อเลขในเอกสารนี้ ต้องรันเอง

### ขนาดโฟลเดอร์ไฟล์ที่เว็บรุ่น 2 ดึงไปใช้

หัวข้อ ⑧ ของสคริปต์พิมพ์ออกมาว่ามี 221 ไฟล์ รวม 103,242,456 ไบต์ (98.5 MB)
แบ่งเป็นไฟล์เล่ม 66 ไฟล์ 92,248,363 ไบต์ ไฟล์พจนานุกรม 144 ไฟล์ 9,405,136 ไบต์
และไฟล์คำอธิบายประกอบ 3 ไฟล์ 324,193 ไบต์

**โฟลเดอร์นี้ไม่ได้เอาไปคิดในเลข 134.5 เมกะไบต์** เพราะเป็นของเดียวกับที่อยู่ในฐานข้อมูล
แค่แปลงรูปไว้ให้เว็บรุ่น 2 อ่านง่าย นับสองรอบคือนับซ้ำ

**ส่วนไฟล์คำอธิบายประกอบ 3 ไฟล์นั้นรุ่น 3 ไม่เอาเลย** เปิดดูแล้วเป็นบทความที่ผู้เขียนของรุ่น 2 เขียนเอง
และในเนื้ออ้าง Wallace ซึ่ง [WPA.08](../wpa-08-mission-statement.md) หัวข้อ Out ข้อ 1 ห้ามใช้เป็นแหล่ง

## ที่ยังไม่ได้พิสูจน์

1. **เลข 134.5 เมกะไบต์เป็นการประมาณ ไม่ใช่ของที่วัดจาก Postgres จริง**
   เครื่องนี้ไม่มี Postgres และไม่มี docker ให้ตั้งขึ้นมาลอง (`Get-Command psql, pg_ctl, docker, initdb` ไม่เจอสักตัว)
   ตัวเลขที่เอามาคูณมาจากวิธีเก็บของที่คู่มือ Postgres บอกไว้ ของจริงจะรู้ก็ต่อเมื่อยกขึ้นไปจริง
   **แต่ข้อสรุปว่าพอไม่สั่นคลอน** เพราะต่อให้ประมาณพลาดเป็น 2 เท่า ก็ยังไม่ถึงครึ่งของ 500 เมกะไบต์

2. **ยังไม่ได้วัดของจริงที่รุ่น 3 จะยกขึ้น** ท่อแปลงข้อมูลของรุ่น 3 ยังไม่ได้รันในโต๊ะนี้
   จึงยังไม่มีโฟลเดอร์ `_ข้อมูลเว็บ/` ให้วัด ที่วัดได้คือของรุ่น 2 ซึ่งจำนวนคำห่างกันแค่ 272 คำ
   **แต่โครงช่องไม่เหมือนกัน** จึงเป็นการประมาณ ไม่ใช่การวัด

3. **ยังไม่ได้บวกของที่รุ่น 3 ต้องมีเพิ่ม** คือ UBS Dictionary, HebrewLexicon และป้ายการเน้น 33 ชนิดของ Levinsohn
   ทั้งสามอย่างไม่มีในฐานข้อมูลของรุ่น 2 เลย จึงไม่มีอะไรให้วัด

4. **ยังไม่รู้ว่าส่งของจริงแล้วจะกินโควตาส่งออกเท่าไร** ตัวเลข 46 กิโลไบต์ต่อบทเป็นเนื้อดิบ
   ยังไม่ได้บวกโครง JSON และยังไม่ได้หักการบีบข้อมูลตอนส่ง

5. **ยังไม่ได้ตรวจว่าเงื่อนไขของแผนฟรีจะเปลี่ยนไหม** อ่านจากเว็บวันที่ 31 ส.ค. 2569 สองหน้าตรงกัน
   วันที่จะยกขึ้นจริงต้องเปิดอ่านซ้ำ **ห้ามเชื่อเลขในเอกสารนี้**

6. **ยังไม่ได้เปิดดูว่าฝั่งกรีกของ MACULA Greek ให้ช่องอะไรบ้าง** รู้แค่ว่าฝั่งกรีกของรุ่น 2 มาจาก OpenGNT ที่เราไม่ใช้
   แต่ยังไม่ได้ทานว่าของ MACULA Greek มีครบเท่ากันไหม ซึ่งกระทบขนาดของ 138,013 แถวนั้น
